# 01. Vision, pillars, product model, targets

## Vision
**The best personal investment assistant for rule-based investors: deep strategies on a few assets, verified with honest analytics, powered by data you bring yourself, and operated through Claude via MCP.**

Longer term: make evidence-backed, professional-grade strategies usable by anyone, including people with little investment knowledge, with honest decisions and visible uncertainty.

## Pillars (priority order)
1. **Reliability.** We never act on wrong data or wrong calculations. Data and math are checked redundantly and independently. When data is in doubt, the tool never presents a normal signal: yellow status computes with a visible warning; red status switches to the strategy's declared safe state and tells the user exactly what to do.
2. **Evidence.** Strategies are grounded in published research, verified with robustness and overfitting statistics, and judged on forward (post-registration) results, which are tamper-evident.
3. **Decision clarity.** Every choice is shown as trade-offs in the base currency and in ranges (return, bad-case loss, recovery time, costs, tax), so the user decides knowingly. The tool educates on decisions, not finance theory.
4. **Accessibility.** Professional methods usable without understanding the math, executable at a real broker with real costs, real execution timing and real tax.
5. **Honesty and protection** (cross-cutting). Show uncertainty and luck, never oversell, make risks impossible to miss.

## Product model
- **Closed, personal app.** Each install serves a few accounts (a family) with one or more admins. No sign-up page, no public pages, no public demo. Each person sees only their own strategies, positions, journal and tax data; market data, checks, data health and the strategy library are shared within the install.
- **Bring your own data.** The public repo ships the app, the plug-in framework, public plug-ins for official APIs and a runnable template. Each admin chooses and writes plug-ins for their own sources and is responsible for their terms (15).
- **Works anywhere.** Base currency, time zone, languages, asset universe, benchmarks, broker costs and tax regime are admin choices or plug-ins, never code edits. The owner's install uses JPY, Asia/Tokyo, English and Japanese, and the Japan tax regime.
- **Self-hosted** on an always-on machine of the admin's own, reached through a tunnel (12). A demo account (same security as any account, sample strategies, no personal data) is used to show the app to someone.
- **Template-worthy, source-available.** Anyone can clone and run their own install under PolyForm Noncommercial 1.0.0. Commercial use is not a goal.

## Audience
The owner and their family first; designed so an individual with little investment knowledge can use it, in their own languages.

## Benchmark set
Judged in the base currency, after tax and costs, against what an individual would realistically hold. Index benchmarks are assumed held in the regime's best tax-advantaged account (e.g. NISA in Japan), because that is the realistic alternative. The set is an admin setting; the owner's install uses:
- S&P 500 index fund in NISA (modeled with SPY in yen minus fee)
- Global index fund in NISA (eMAXIS Slim All Country; modeled with VT in yen minus fee)
- Balanced 8-asset fund in NISA (ETF composite, defined in C2)
- Robo-advisor style portfolio (ETF mix, defined in C2)
- Gold (GLD in yen)
- Bank deposits (actual current deposit rate)

## Outcome targets
Targets apply to a **strategy slice**, not the whole portfolio (the user may hold e.g. 50% in a safe core and 10% in an aggressive strategy). Measured on the **median rolling 5-year window**, with the share of windows meeting the target and a confidence range always reported. Backtests use next-day execution, realistic costs and tax. The targets below are the owner's, measured on the owner's install (JPY, Japan regime).

| Tier | Target |
|---|---|
| Aggressive (default) | Beat S&P 500 buy and hold held in NISA by 5-10pp per year in yen after tax and costs, with max drawdown no worse than S&P 500's and higher Sharpe and Calmar ratios |
| Balanced | Match All Country (NISA) return with at most 60% of its max drawdown |
| Conservative | Beat the balanced 8-asset fund (NISA) with no worse max drawdown |

Initial evidence for the aggressive target: `docs/evidence/backtests.md` (pre-tax, same-close execution; re-run with next-day execution and tax at TR1). Whole-portfolio targets are defined at F5.

# 04. Data pipeline (pillar 1)

## Sources and roles
Every source is a plug-in (15). Plug-ins suggest a role; the admin assigns roles in Settings:
- **Primary:** the canonical source for a data kind. Its values are what calculations use.
- **Secondary:** an independent source used for cross-checks (layer B) and, under the rules below, as a stand-in when the primary is missing. More than one secondary may be assigned.
- **Check:** used only for verification (layers C and D), never as a value.

Default plug-ins for the owner's install (to be confirmed in A1; limits and terms verified and recorded in `docs/data-spike.md`):

| Data kind | Role | Source | Plug-in | Notes (verify in A1) |
|---|---|---|---|---|
| Daily bars | Primary | Tiingo (free Starter) | Public | Official API, BYOK. 500 unique symbols/month, 50 requests/hour, 1,000/day, 30+ years. Personal, internal use. |
| Daily bars | Secondary (candidates) | Alpaca market data (free Basic: consolidated data from 2016, 200 calls/min); Massive, formerly Polygon (free: end-of-day, 2 years, 5 calls/min, individual use) | Public | Official APIs. A1 evaluates both; one or both become secondaries. |
| Daily bars | Secondary (history) | Yahoo Finance via `yahoo-finance2` | Private | Unofficial. Its "close" is already split-adjusted (un-split before comparing). The only free secondary with 30+ years, so it covers full-history checks. |
| Issuer data (best effort) | Check | ETF issuer websites: daily NAV, distributions, splits | Private | Formats vary. A check, not a gate. |
| Daily FX (USD/base) | Primary | ECB euro reference rates (USD/JPY as a cross) | Public | Daily valuation. No rates on TARGET holidays. |
| Daily FX | Secondary | Yahoo `JPY=X`; FRED `DEXJPUS` (weekly, H.10, New York noon) | Private / public | Cross-checks. |
| FX for tax | Primary | Broker-style rates (TTM/TTS/TTB), e.g. a bank's published daily rates | Private | Used by the tax engine (07), as the tax regime requires. Source chosen in C1. |
| Cash rates | Primary | FRED `DTB3` (USD T-bill); deposit rate for the base currency (admin setting, actual current rate) | Public / setting | `DTB3` is published the next business day and is missing on bond-market holidays. |
| Independent index check | Check | FRED `SP500` | Public | 10 years only, price index. |
| Event calendar (F1) | Primary | Federal Reserve (FOMC), BLS (CPI, jobs report) | Public | Versioned static data. |

Rejected for v1: Stooq (key required, unclear terms), Alpha Vantage (25 requests/day), Twelve Data free, EODHD free (20 calls/day). Paid upgrades only with owner approval: Tiingo Power ($30/month), Norgate, EODHD.

## What is imported
| Data | Fields | Use |
|---|---|---|
| Daily bars | date, open, high, low, unadjusted close, volume, dividend cash, split factor | All calculations |
| Provider adjusted values | adjClose (Tiingo, Yahoo), Yahoo split-adjusted close | Cross-checks only |
| Issuer data | NAV, distributions, splits | Cross-checks (layer D) |
| Ticker metadata | inception date, exchange, active status | Validation, warm-up, history disclosure |
| Rates, FX, index | DTB3, deposit rate, ECB rates, DEXJPUS, SP500 | Cash, leverage cost, base-currency valuation, sanity checks |

No indicators, signals or derived series are imported.

## Import schedule
- **Bootstrap:** full history from all sources.
- **Daily:** an hourly timer on the server runs the daily job **once per trading day**, at the first check after the day's data is final (time measured in A1). It fetches the last 10 trading days for every ticker in use (the overlap catches late corrections), issuer data, FX and rates. A run that did not finish is retried at the next check; data still missing stays `pending` and is retried. Catch-up covers every unprocessed trading day (e.g. after the server was off).
- **Upserts** go through a **revision log** (old value, new value, source, time); stored data is never silently overwritten. The log covers raw fields only (open, high, low, unadjusted close, volume, dividend, split). Provider-adjusted values (Tiingo `adjClose`, Yahoo split-adjusted closes), which providers rewrite for the whole history after every dividend or split, keep the latest snapshot plus one **re-adjustment event** per refetch (source, date range, implied factor); they are used only for return comparisons, which a rescaling does not change.
- **Weekly:** full-history refetch and diff; changes go to the revision log and trigger recomputation.
- **Retries:** through the plug-in SDK's HTTP client (backoff, per-source caps). A source that refuses (403, 429) is stopped for the run.
- **Calendars:** NYSE holidays and half-days, bond-market holidays and ECB (TARGET) holidays from versioned static tables.
- **Manual fallback:** validated CSV import.
- **Quota guard:** each plug-in declares its provider's limits; the SDK never goes above 80% of any of them.

## Point-in-time series (rates, FX, index)
- The value of a series for trading date D is the **last value published as of the run** (`asOf(series, D)`). One shared function serves the live pipeline and the backtester, so a backtest never uses a value the live run could not have had (no look-ahead).
- Expected gaps (known holidays of that series' calendar) are green. Unexpected gaps are yellow. Staleness beyond 5 business days is red.
- FX health affects only base-currency valuation and tax, never a signal computed in USD.
- Assumption: daily cash accrual and synthetic leverage cost use the last published `DTB3` (one-day lag).

## What is calculated
Adjusted series: a **forward-accumulated total-return index** from raw close, dividends and splits (1.0 on the first date; a new dividend never changes past values, so incremental and full recomputation match exactly and signals on total-return series are unaffected, since they compare values of the same series); daily returns; daily cash returns (USD and base currency); synthetic leverage; base-currency series; indicators (06); signals; allocations; equity curves; tax (07); metrics; statistics (09).

## Verification layers
| Layer | Check | Default tolerance | Frequency |
|---|---|---|---|
| A. Bar validation | Prices > 0; high ≥ max(open, close); low ≤ min(open, close); volume ≥ 0; no duplicates; trading days only; flag moves > 25% (1x) or > 60% (3x); flag unchanged close for 2+ days | As stated | Every bar |
| B. Cross-source | Raw close: primary vs each secondary (after un-splitting Yahoo) | ≤ 0.05% | Daily |
| | Dividend and split events match | Exact dates, ≤ 1% amounts | Daily |

| C. Economic sanity | Daily return of SSO ≈ 2x, UPRO/SPXL ≈ 3x SPY; QLD ≈ 2x, TQQQ ≈ 3x QQQ | Volatility-scaled: 0.5pp + 10% of the absolute expected move; ex-dividend days adjusted (leveraged ETFs track the index, not SPY) | Daily |
| | SPY daily return vs FRED S&P 500 index return | ≤ 0.1pp (ex-dividend adjusted); covers the last 10 years only | Daily |
| D. Issuer reconciliation (best effort) | Market close vs issuer NAV within normal premium/discount; distributions and splits match issuer records | Per-ETF thresholds set in A3 | Daily |

Separately: a day with a single source is never green. | 100% of material faults | Every commit |

**Storage of results:** daily runs store every check result. Weekly full-history passes store every non-green result in full and one summary row per (run, layer, check) with counts and the largest deviation. Every check still runs on every bar.

## Severity rules
| Situation | Status |
|---|---|
| All checks pass | Green |
| A secondary source, issuer site or FX cross-check unavailable; a mismatch within 2x tolerance; a single-day layer C deviation within 3x tolerance | Yellow |
| Primary data missing with no usable stand-in (below); layer A failure; mismatch above 2x tolerance; layer C deviation above 3x tolerance or repeated 3 days | Red |

### Primary missing, secondary present (automatic, no human decision)
1. The secondary bar for day D must pass layer A, and layer C where it applies. If two or more secondaries are available, they must agree within layer B tolerance. Otherwise: red.
2. **Decision-margin test:** each affected strategy's signals are recomputed with the stand-in price moved up and down by an uncertainty band. The band is the tolerance of the tightest independent check that passed that day: layer B tolerance when two secondaries agree, 0.1pp when SPY matched the FRED index, otherwise the layer C tolerance. If no signal can flip within the band: **yellow** ("secondary source only"). If any could: **red for that strategy only**.
3. At most 2 stand-in days in a row per ticker; the 3rd is red.
4. When the primary's value for D arrives, layer B compares it with the stand-in. A mismatch above tolerance goes to the revision log, annotates the forward record (never edits it) and alerts: "D's signal used a secondary price that was off by X; with the corrected price it would have been Y."

Stand-in bars are stored as raw data from their source; the canonical bar records which source it came from.

## Fail-closed behavior and safe state
- **Yellow:** signals are computed; every alert and screen shows the warning and reason.
- **Red:** no normal signal is presented for strategies depending on the affected data. Each strategy declares a **safe state** (default for leveraged strategies: 1x of the underlying; user can choose cash). The alert says: "Data unreliable today. Your strategy's safe action is X," with exact instructions. The safe state is recorded in the forward record as such.
- Status appears on the dashboard, in every alert, in every MCP response about signals, and in the audit report.

## Storage, keys, budget
- A SQLite file on the server (12). Database size and free disk on the admin page; warn at 70% of disk.
- BYOK: provider keys live in the server's `.env`, at install level (market data is shared by the install's accounts). Plug-ins read them; the web app never needs them.
- No paid service until free genuinely limits a robust system, and only with owner approval.

# 05. Strategy model

## Strategies
- Unlimited strategies; detail view; side-by-side comparison of up to 4.
- testfol-style model, extended:
  - **Signals:** comparisons of indicators or thresholds; options `totalReturn`, `delayDays`, `tolerancePct` (percent, symmetric hysteresis); derived (NOT) and aggregate (AND/OR) signals; **ensemble signals** (vote across several signals; output = share agreeing).
  - **Allocations:** ordered priority chain with any number of fallbacks; first allocation whose conditions are true is active; last is an unconditional fallback. **Filtered fallbacks** through the chain (e.g. bonds only if bonds are above their own trend, else cash).
  - **Holdings:** fixed weights; **ranked blocks** (top N by an indicator); **exposure scaling** (volatility targeting in discrete steps across 0x/1x/2x/3x instruments; ensemble share can also scale exposure).
  - **Drawdown circuit breaker** (optional).
  - **Synthetic leverage:** `SPY?L=3&E=0.9`, daily return = L * r - (L - 1) * cashRate/252 - E/100/252.
  - **Cash:** `CASH_USD` (USD T-bill yield, carries FX exposure in base-currency terms) or `CASH_BASE` (the base currency's deposit rate, an admin setting; converting incurs FX spread and may realize taxable gains). Decision cards show the base-currency impact of either choice.
  - **Safe state** (required for every strategy, see 04).
  - **Trading frequency:** daily, weekly, monthly. **Costs:** slippage (bps), fees and FX spread, defaulting to the install's broker cost settings (C2).
  - **Account type:** one of the account types the install's tax regime defines (07); every regime defines a `taxable` default. Tax-advantaged accounts where eligible.
- **Tolerance semantics:** true when value > ref * (1 + tolerancePct/100); false when value < ref * (1 - tolerancePct/100); otherwise unchanged. Initial state on the first valid day: plain comparison (value > ref). Verified against testfol parity.

## Execution model
- Signals are computed from a close once the day's data is final (the next morning in Japan); the earliest realistic trade is the next US session.
- `execution: next_open | next_close | same_close`. **Default: next_open** (with slippage) for backtests, forward tracking and alerts.
- `same_close` exists only for testfol parity tests and is labeled "not achievable: it trades at a close that is not yet known" wherever shown.
- Small amounts: optional whole-share modeling in backtests; the rebalance calculator always rounds to whole shares and shows residual cash.

## Versions and registration
- **Draft** strategies can be edited and backtested freely; they create no forward record.
- **Registering** a strategy creates an immutable StrategyVersion and starts its forward record. Edits to a registered strategy create a new draft.
- **Tamper-evident record:** each registration and each daily forward entry is hash-chained (each entry includes the hash of the previous), and chain heads are timestamped externally (e.g. signed git tags or OpenTimestamps), so "registered on date X, and every day since" is provable.
- The forward record stores what was actually signaled at the time (including safe-state days); later recomputations are annotations, never edits.

## YAML
Canonical YAML validated by zod; visual builder and YAML round-trip without loss. Keys and values are language-neutral (names are free text). `account` refers to an account type key of the install's tax regime and is validated against it.

```yaml
name: SPY 3x trend + vol filter (ensemble)
account: taxable
execution: next_open
safeState: { holdings: [{ ticker: SPY, weight: 100 }] }
evaluation: { frequency: daily }
costs: { slippageBps: 5, feePct: 0.1, fxSpreadPct: 0.2 }
signals:
  - id: A
    type: ensemble
    members:
      - { left: { indicator: price, ticker: SPY, totalReturn: true }, op: ">", right: { indicator: sma, ticker: SPY, length: 150, totalReturn: true }, tolerancePct: 3 }
      - { left: { indicator: price, ticker: SPY, totalReturn: true }, op: ">", right: { indicator: sma, ticker: SPY, length: 200, totalReturn: true }, tolerancePct: 3 }
      - { left: { indicator: price, ticker: SPY, totalReturn: true }, op: ">", right: { indicator: sma, ticker: SPY, length: 250, totalReturn: true }, tolerancePct: 3 }
    threshold: 0.5
  - id: B
    type: compare
    left:  { indicator: volatility, ticker: SPY, length: 20 }
    op: "<"
    right: { threshold: 25 }
allocations:
  - name: Risk on
    when: { all: [A, B] }
    holdings: [{ ticker: "SPY?L=3&E=0.9", weight: 100 }]
  - name: Trend only
    when: { all: [A] }
    holdings: [{ ticker: SPY, weight: 100 }]
  - name: Cash
    holdings: [{ ticker: CASH_USD, weight: 100 }]
```

# 06. Indicators and numeric rules

All computed locally from verified data, each with documented formula, parameters and warm-up period (`docs/indicators.md` and tooltips in the install's languages).

- **v1:** Price, SMA, EMA, Return over N days, Volatility (close-to-close, sqrt(252)), Parkinson, Garman-Klass and Yang-Zhang volatility, Drawdown from N-day or all-time high, N-day High/Low, Threshold; tolerance bands on any comparison.
- **v1.1:** RSI, MACD, Bollinger Bands, ATR, moving-average slope, relative strength, rolling correlation.
- **Tier 2 (F2):** credit spread level and change, yield curve, NFCI, unemployment trend (Sahm-style), VIX, T-bill rate.

## Numeric rules
- float64 for prices, returns and indicators; decimal.js for money, tax and quotas.
- **Near-ties:** when a compared value is within 1e-9 (relative) of its reference, the comparison is a tie and the previous state is kept. Core and reference implementations apply the same rule; tie days are logged and are not treated as mismatches.
- Annualization uses 252 trading days.

# 07. Accounts and tax

## Model
- **Tax is a plug-in.** Core holds a generic tax engine; a **tax regime plug-in** (15) supplies a country's rules. The admin picks the install's regime in Settings. The public repo ships the Japan regime (below) and a template regime for a made-up country.
- **Accounts are per person.** Each user has their own tax accounts, quota ledger, tax lots and loss carryforward (tax-advantaged accounts such as NISA are per individual by law). The install's regime defines which account types exist.
- Every regime defines a `taxable` account type (the default for timing and leveraged strategies) and any number of tax-advantaged account types.

## What a regime plug-in declares
| Area | Examples |
|---|---|
| Account types | Key, names (per language), taxable or tax-advantaged |
| Eligibility | Which products an account may hold (e.g. no leveraged ETFs), purchase modes (lump sum, periodic only) |
| Quotas | Annual and lifetime limits, how sold amounts free up quota and when |
| Tax on gains and income | Rates on realized gains and on dividends per account type |
| Losses | Offsets (against gains, dividends), carryforward length, conditions (e.g. a filing requirement) |
| Foreign dividends | Withholding at source, foreign tax credit availability per account type |
| Cost basis | Lot method (e.g. moving average), same-day repurchase rules |
| FX for tax | Which rate applies to purchases, sales and dividends (e.g. TTM, TTS, TTB) |
| Transfers | Whether holdings can move between account types (if not, a "move" is sell + rebuy, with both costs shown) |
| Texts | Every user-facing name and explanation, in the plug-in's language files |

The engine computes; the regime only declares. Rules that cannot be declared with the contract are a reason to extend the contract (at a stage review), never to put country code in core.

## Japan regime (public plug-in, the owner's install)
- **特定口座 (`taxable`):** where timing and leveraged strategies live.
- **NISA (opt-in per user):** for the steady core and DCA plans. Timing strategies generally do not fit NISA: quota frees up only the following year, and つみたて投資枠 allows periodic purchases only.
- Holdings cannot be moved from 特定口座 into NISA; a "fallback to NISA" means selling (possibly taxable) and rebuying (using quota). The tool shows both costs.

| Rule | NISA 成長投資枠 | NISA つみたて投資枠 | 特定口座 |
|---|---|---|---|
| Leveraged products | Not eligible | Not eligible | Allowed |
| Eligible products | Listed stocks/ETFs and eligible funds | FSA-designated funds only (labeled ETF proxies until local fund data exists) | All |
| Purchases | Lump sum or periodic | Periodic (DCA) only | Any |
| Annual quota | ¥2.4M | ¥1.2M | n/a |
| Lifetime limit | ¥18M shared (成長 max ¥12M); sold amounts free up quota the next year at book value | Same shared limit | n/a |
| Tax on gains | None | None | 20.315% on realized gains |
| Losses | No offset | No offset | Offset gains and dividends; 3-year carryforward via 確定申告 |
| US ETF dividends | 10% US withholding, no foreign tax credit | Same | Withholding + Japanese tax; foreign tax credit possible |

- A quota tracker shows each user's annual and lifetime usage; the tool warns before and blocks any plan that would exceed limits.
- The owner (tax background) verifies all Japan rules, including the FX convention for foreign-currency trades, before C1 implementation.

## Tax engine
Tax lots; realized gains per switch using the regime's FX convention; loss offsets and carryforward; dividend withholding; quota ledger. Hooks in the backtester from B1; completed in C1. Verified with owner-computed golden cases (no second implementation for tax). The template regime has its own golden cases.

## Tax-free vs taxable comparison
- Same period, in the base currency, after tax; taxable strategies on **liquidation value**.
- Rolling 5-year windows showing which approach won and by how much.
- Hybrid view: tax-advantaged core plus taxable satellite.

## Tax optimization (F4, candidate to pull earlier)
Declared by the regime where it applies. For Japan: asset location (what belongs in NISA vs 特定口座 given quota); year-end loss harvesting in 特定口座 (respecting cost-basis averaging rules for same-day repurchases); choosing December vs January for realizing gains.

# 08. UX, language, decision clarity

## Languages (mandatory)
- Code, comments, commits, database values and technical docs are in US English. Every user-facing text goes through `packages/content` (next-intl message files); no hardcoded user-facing text anywhere, including plug-ins (each plug-in ships its own message files).
- **The install runs in any two languages, neither of which has to be English** (e.g. Portuguese + Spanish). The admin picks a primary language (sign-in page, default) and an optional secondary one (the toggle) in Settings, from the installed language files. Each user switches between the two; the choice is stored in their settings.
- `en.json` is the base file and holds every text. Other language files may be partial; a missing text falls back to English. Languages are found from the files at build time, so anyone can add one.
- `pnpm languages` lists what each language lacks. From D1, CI fails when a language the owner's install uses (EN, JA) lacks a text; other installs run the same check for their own languages.
- Covered: every screen, tooltip, help panel, guided tour, glossary entry, decision card, chart label, error, empty state, alert, export header and user guide. The README and docs in `docs/` are English.
- Locale-aware dates, numbers, currency and percentages, following the page's language and the base currency.
- Natural financial terminology per language (e.g. 最大ドローダウン in Japanese); regime-specific terms (e.g. 特定口座) live in the tax regime plug-in's files. The owner reviews Japanese.
- Alerts in each user's selected language.

## Defaults instead of questionnaires
- One opinionated default: aggressive tier, leverage only in favorable conditions, parameter ensembles instead of single parameters, frequent fallbacks, the regime's taxable account, next-day execution.
- All assumptions (tier, drawdown limit, example amount, costs, FX spread, cash currency, account type, execution, safe state) visible and editable. Default example amount: an admin setting in the base currency (the owner's install: ¥100,000), with whole-share effects shown.
- Risks (leverage, drawdown, tax, gap risk, short asset histories) shown clearly before a risky setting takes effect. No profiling quiz.

## Decision card (every strategy, fallback comparison and finder candidate)
- Return range (10th-90th percentile over 5 years) and median, not a single number.
- Bad-case and historical worst-case loss **in the base currency** for the user's amount; time to recover.
- Costs, FX and tax drag; eligibility for the regime's tax-advantaged accounts.
- What happens if the user deviates (quits at the bottom, delays re-entry).
- Comparison against the install's benchmark set (01).
- History length and crisis coverage; wide confidence ranges flagged.
- Plain-language verdict of the trade-off.

## Information-parity metric set (every strategy)
CAGR, cumulative return, volatility, downside deviation, Sharpe, Sortino, Calmar, max drawdown, average drawdown, longest drawdown and recovery time, Ulcer index, beta and correlation vs S&P 500 and All Country, VaR 95%, CVaR 95%, best and worst year, % positive months, rolling 5-year return range (median and share meeting target), switches per year, average exposure/leverage, cost drag, tax drag, deflated Sharpe ratio, probability of backtest overfitting.

## Guidance
- Tooltips on every metric, indicator, setting, column and chart element (definition, why it matters, example), in the install's languages, coverage enforced in CI.
- "How to use this page" panel on every page; onboarding checklist; replayable guided tours; glossary; plain-language summaries above numbers; empty states and errors that say what to do next.
- Starter templates (buy and hold SPY, ensemble trend filter, owner's Setup 1 with ensemble, dual momentum), each with a decision card.
- User guide in the app, from message files (so it follows the install's languages). Mobile-friendly, dark mode.
- A UI feature is done only when its guidance content exists in `en.json` and in the owner's install languages (EN, JA).

## Acceptance (before v1)
3-5 test users unfamiliar with the tool, on the owner's install (demo account or their own), complete onboarding to a first alert with in-app guidance only (in their chosen language); at least 4 of 5 correctly state a strategy's bad-case loss in the base currency.

# 09. Analytics: robustness, statistics, Monte Carlo, library, finder

## Robustness score components
| Component | Question | Measurement | Display example |
|---|---|---|---|
| Parameter stability | Only works at one setting? | % of neighboring parameter sets beating the benchmark risk-adjusted | "82% of nearby settings also work" |
| Time stability | Works across periods? | % of walk-forward folds beating the benchmark | "Won in 7 of 10 periods" |
| Crisis survival | Protects when it matters? | Drawdown vs benchmark in 2000-02, 2008, 2020, 2022 (only those covered by data, stated) | "Passed 3 of 4 crises" |
| Statistical confidence | Could it be luck? | Bootstrap (block) p-value of the edge, adjusted for the effective number of independent trials | "Results this good would appear 6% of the time with no edge" |
| Live decay | Still works after registration? | Forward vs backtest Sharpe | "Live results in line with backtest" |

Benchmark calibrated to about 50; weakest-link aggregation (geometric mean, capped by the weakest component); "insufficient data" when history is too short.

## Overfitting statistics (shown alongside the score)
- **Deflated Sharpe ratio** and **probability of backtest overfitting** (combinatorially symmetric cross-validation), both from Bailey and López de Prado, using the effective number of independent trials (not the raw count).

## Score validation (pre-registered)
- The formula is written in `docs/robustness-score.md` and approved by the owner **before** any validation is run.
- Known-answer tests: random-entry median ≤ 35; deliberately over-optimized ≤ 40; benchmark 45-55.
- Predictive check: run **once** on a held-out period not used to design the formula; the result is recorded in `docs/robustness-score.md` whatever it is. Any revision is logged with its reason and validated only on data not used in earlier attempts. Never iterate until it passes.

## Monte Carlo goal projection
**Block bootstrap of the underlying asset returns** (preserving volatility clustering and autocorrelation), then re-run the strategy on each simulated path. Output: probability of reaching a user goal (e.g. 100,000 to 300,000 in the base currency in 5 years), including contribution plans.

## Strategy library
- 10-15 strategy families with parameter variants (up to about 100 registered variants), in `library/`, approved by the owner before seeding (B2).
- Every family cites its research basis in `docs/strategy-library.md`. Candidate references to verify: Faber (2007) tactical asset allocation; Moskowitz, Ooi and Pedersen (2012) time-series momentum; Antonacci (2014) dual momentum; Moreira and Muir (2017) volatility-managed portfolios; Cheng and Madhavan (2009) leveraged ETF dynamics; Gayed and Bilello (2016) leverage with moving-average rules; McLean and Pontiff (2016) post-publication decay; Bailey and López de Prado (deflated Sharpe, backtest overfitting).
- Parameter ensembles preferred over single parameters. Assume edges decay after publication; judge on post-registration results. Immutable once registered. No curated risk profiles.

## Finder behavior
- Always-visible panel comparing library strategies (and optionally the user's other strategies) against a chosen user strategy. Top 10 candidates (tentative).
- **Ranked on long-run robustness**, not recent performance: after-tax risk-adjusted results over full history with next-day execution, robustness score, deflated Sharpe. Recent forward results are a sanity check, not a trigger.
- Per candidate: metrics, decision card, tier ("Watch" / "Consider switching"), "qualifying for N days", "Add to my strategies" (the copy starts as a draft).
- Hysteresis on the ranking score to keep the list stable. Suggests only; never switches automatically.

## Finder default criteria (all configurable)
- **Eligibility:** registered ≥ 6 months; robustness score ≥ 60; probability of backtest overfitting ≤ 0.3; volatility within ±25% and same leverage class; ≤ 12 switches per year; account-type eligible.
- **Consider switching (all must hold):** long-run Sharpe ≥ user's + 0.2 and Calmar ≥ user's, with ≥ 90% confidence after the luck check; max drawdown no worse than user's + 2pp; forward results inside the candidate's expected range; estimated after-tax benefit exceeds the switching cost (tax, fees, FX) within 3 years.
- **Watch:** passes eligibility and most switching criteria.
- 12-month forward performance is shown as information only.
- Cost model before C1: the regime's flat rate on realized gains (Japan: 20.315%) plus the install's broker fee and FX spread settings (editable).

## Finder integrity
Luck check ("N qualify; about M would by luck alone"; no "Consider switching" unless N clearly exceeds M); no look-ahead; finder self-test (follow suggestions vs stay) shown on the panel; optional notifications (20 consecutive days in "Consider switching", 6-month cooldown).

# 10. MCP server and AI export

The app makes no LLM calls. Claude is used on request through MCP within the owner's Claude plan.

## Level 1: read-only (E1, in v1)
- Tools: strategies and versions; YAML; current state with data-health status; backtests on demand (in memory, nothing persisted); forward results with chain verification status; positions, trades and journal; decision cards; tax comparisons; data-health and audit reports.
- No database writes, no notifications. Reads the **analysis copy** (the latest daily backup, unpacked on the machine running Claude), opened read-only, for one user (`--user <username>`): that user's data plus shared data. Never deployed.
- Sources whose terms forbid giving their data to AI models (`noAi`, 15) are left out: their raw values never appear in responses, only results computed from them, and only if their terms allow that.

## AI export
UI button, CLI and MCP tool producing a compact bundle: Markdown summary + JSON (YAML, key stats, downsampled equity, switches, forward vs backtest). Default under 20,000 characters.

## Context pack (on request only)
Exposures (effective leverage, asset mix, account mix, base-currency and USD cash exposure, rate sensitivity), signal state and regime history (from B3), for Claude to combine with current news and produce scenarios (base/bear/bull, what the strategy would do in each) for 6-month, 1, 3 and 5-year horizons.

## Level 2 (F6) and level 3 (F7)
- Level 2: natural-language strategy building (YAML validated by the same schema; creates drafts only), save backtests, add finder candidates.
- Level 3: trades, journal entries, notification settings; destructive actions require explicit confirmation.

## General
Local stdio server (`pnpm mcp --user <username>`) for Claude Code and Claude Desktop. Compact responses; long series downsampled; signal responses include data-health status.

# 11. Alerts and notifications

## Channels
Discord and Telegram, configured per user in Settings (stored encrypted). Admins also get operational alerts (failed jobs, data health, server updates, the address down). Email and LINE in the backlog. Alerts in each user's selected language.

## Alert types
| Alert | When | Stage |
|---|---|---|
| Strategy state change | Active allocation changes; states the execution timing (e.g. "trade at the next US open") | A2 |
| Data health | Yellow (warning) or red (safe-state action with exact instructions) | A2 |
| Job failure | Admins | A2 |
| Position mismatch | Holdings differ from target; includes rebalance calculator orders (whole shares) | D1 |
| Strategy health | Live drawdown exceeds the worst 5% predicted by the backtest | D2 |
| Key-day alert | Before an important US session | F1 |
| Finder | Optional (see 09) | F3 |

Every alert states the data-health status. Idempotent per (strategy version, trading date, alert type).

## Key-day alerts (F1, right after v1)
- Sent a few hours before the US open (around 21:00 JST on the owner's install) when a scheduled event (FOMC, CPI, jobs report), signal proximity (close near a threshold) or stress state (volatility spike, large prior-day drop) makes the session important.
- Contents: why it matters, precomputed price levels, suggested pre-session stop orders (order types and validity are a broker setting; the owner's broker verified in F1).
- Backtested with daily OHLC (fill at the stop, or at the open on gaps, plus slippage). Capped frequency, ranked by severity. On by default only if it improves after-tax risk-adjusted results.

## Accounts and access
- A few accounts per install, one or more admins. **No sign-up page.** The first account (an admin) is made from the CLI: `pnpm user create <username>`. Afterwards admins manage accounts in Settings > Admin > Accounts (create, reset password or authenticator, revoke devices, disable), each task confirmed with the admin's own authenticator code; a new account or reset gives a one-time setup link (24 hours).
- Sign-in: username + password + authenticator code (TOTP), or one of 8 one-time backup codes. **At most 2 devices per account**; a third is refused until one is revoked. Sign-in checks the account's device slots first. Every refusal at the password step (unknown user, wrong password, disabled account, both slots taken, authenticator not set up yet) shows one message: "Wrong username or password, or this account is already signed in on 2 devices or not set up yet. Sign out on one of its devices, or ask the admin." Every path does the same work (the password hash, a dummy one when the user is unknown, and the device count), so response times give nothing away, and every refusal counts toward lockout. A third device never reaches the authenticator step. A "2 devices" refusal at the authenticator step is allowed only when another device signed in meanwhile (the person has already proven password and code). Lockout: 5 failures per IP per 15 min, 10 per username per hour, 50 overall per hour.
- Authorization is checked in every server action and route handler (never only in middleware), and every query on a user table is scoped by `owner_id`. Tests call each server action as the wrong user.
- **Demo account:** a normal account (same sign-in and device rules) filled with sample strategies, positions and journal entries by `pnpm demo <username>` (only accounts named `demo*` are touched), on the install's real market data. Used to show the app to someone.

## Admin settings (install-wide, no code edits)
Base currency (chosen before anything is stored), time zone (default display; trading dates stay America/New_York), primary and secondary language, asset universe, source roles and order (04), benchmark set (01), broker cost defaults, deposit rate, tax regime (07), default example amount, alert channels for admins. Each user has their own language, notification channels, tax accounts and defaults.

## Compute placement
Heavy computation (robustness sweeps, Monte Carlo, library evaluation) runs in server jobs (with lower CPU priority, see hosting) or in the browser (Web Workers), never in a web request. Results are stored and displayed.

`plugins/` is not a pnpm workspace member (the public lockfile never depends on it); it imports `@saku/*` through the root `node_modules`, and typecheck and tests include it when present. Commit inside it first, then commit the pointer in the main repo.

## Hosting (self-hosted)
- One always-on machine (the owner's: a mini PC with Ubuntu Server, shared with Tora) runs everything as plain systemd services under the owner's user, no Docker:
  - `saku-app`: the web app on `127.0.0.1:3001` only.
  - `saku-daily.timer`: hourly check; runs the daily job once per trading day (04), then the backup and admin alerts. Weekly and monthly jobs through the same script, each with its own stamp and lock.
  - `saku-update.timer`: pulls new commits (both repos), installs, migrates, builds, restarts, checks the app answers; rolls back and alerts admins on failure; never while a job runs.
  - Heavy jobs run with `Nice=10` and a `CPUQuota`, so other apps on the machine stay responsive.
- Folders: `~/.local/share/saku/` (database, backups, analysis copy), `~/.local/state/saku/` (logs, stamps, locks); `SAKU_STATE_DIR` for a second copy on the same machine.
- Address: Tailscale Funnel on its own port (owner: `tailscale funnel --bg --https=8443 3001`). No router port opened.
- Backups: a daily compressed copy of the database (30 days plus the first of each month for 12 months), copied off the machine (the owner: to their PC over ssh). `pnpm restore` loads a copy into a new, empty database only. Each user can download their own data (JSON) and load it into an empty account.
- Outside watch: healthchecks.io gets a ping after each full daily success; it alerts when pings stop (the machine cannot report its own outage).
- Hosted options (e.g. Vercel + Turso) are not supported in v1; libSQL keeps them possible later.

## Risks of self-hosting
| Risk | Mitigation |
|---|---|
| The machine or network is down at run time | Hourly check catches up; a signal is for the next US session, so there are hours of slack; healthchecks.io alerts when pings stop |
| Disk failure | Daily backups off the machine; chain anchors kept with the backups |
| Clock drift (chain timestamps) | NTP on; clock offset shown on the admin page |
| Public address | Password + TOTP + lockout + 2 devices; authorization in every server action; Next.js kept patched (dependency updates reviewed monthly) |
| A provider changes or blocks | Secondary sources and roles (04); a blocked source stops for the run, never worked around |

## Non-functional
- Security: as above; secrets (provider keys, `AUTH_SECRET`) only in the server's `.env`; alert channel targets encrypted at rest; no keys or market data in the public repo; MCP read-only.
- Observability: job runs table, structured logs, admin pages (server status, runs, freshness, checks, database size and disk, quotas, chain status, activity log).
- Performance: 30-year daily backtest < 2 s; nightly library evaluation < 5 min; one robustness sweep < 2 min, measured on the owner's machine (Intel N150 class).
- Disclaimer: "not financial advice"; data accuracy not guaranteed, health status shown (in the install's languages).

- `README.md`: what Saku is, quick start (local, with the demo seed), the guide table. Guides in `docs/`, one per topic: setup (machine, first user, first settings), plug-ins (contracts, template, testing), running (jobs, schedule, logs), backups, languages, data pipeline, indicators, troubleshooting.

# 13. Testing and parity

- Vitest (unit, integration), fast-check (property tests), Playwright (E2E).
- **External golden values first:** testfol parity, TradingView-verified indicator values, owner hand-computed tax cases (and the template regime's own cases). These catch spec misreadings that two Claude-written implementations would share.
- Core vs reference implementation (core math only) with near-tie handling (06).
- Incremental vs full recomputation (≤ 1e-9).
- Fault-injection suite (material faults), robustness score known-answer tests, chain verification tests, authorization tests (every server action called as the wrong user).
- No live calls in tests.

## Fixtures and where tests run
| Data | Where it lives | Runs |
|---|---|---|
| Synthetic bars and provider responses in each provider's exact shape | Public repo (`fixtures/`, plug-in tests, the templates) | `pnpm check:all` and GitHub Actions CI on every push |
| Real recorded provider responses | Private submodule (`plugins/test/fixtures`) | Locally and on the server when the submodule is present |
| Real market data (full history) | The server's database | `pnpm verify` on the server, weekly: testfol parity, core vs reference, incremental vs full, layer checks over full history. Results stored and shown on the admin page; a failure alerts admins. |

Market data and testfol daily equity curves are never committed to the public repo; testfol summary stats may be.

- CI gates (GitHub Actions on the public repo, synthetic data only, no secrets): lint, typecheck, tests, build, `REQUIREMENTS.md` up to date (`pnpm docs:check`), tooltip and metric coverage; language coverage from D1.

## testfol parity
- Fixtures in `plugins/test/testfol/<case>/` (private, real data): YAML, date range, stats, daily equity CSV if available. Summary stats may also be kept in the public `docs/parity.md`.
- Use SPY (not SPYSIM), start after 1993-02-01, `execution: same_close` (testfol's timing).
- Tolerances: CAGR ± 0.3pp, max drawdown ± 1.0pp, switches ± 5%. Differences documented in `docs/parity.md`.

# 15. Plug-ins

## Rule of thumb
If something is particular to one country, provider, broker, site or person's usage, it is a plug-in or an admin setting, never core code. If a plug-in could serve others as an example and uses an official API, it can go public with neutral names. Anything unofficial, scraped or personal stays private.

## Kinds
Contracts are typed interfaces in `packages/plugin-sdk`. A plug-in package exports one array per kind from `src/index.ts` and may export only the kinds it has.

| Kind | Provides | Stage |
|---|---|---|
| `BarSource` | Daily bars (raw fields, provider adjusted values for checks), ticker metadata | A1 |
| `SeriesSource` | Dated series: cash rates, index levels, later macro series | A1 (F2 for macro) |
| `FxSource` | Daily exchange rates for valuation | A1 |
| `TaxFxSource` | Broker-style rates for tax (TTM/TTS/TTB or the regime's equivalent) | C1 |
| `IssuerSource` | NAV, distributions, splits from fund issuers | A3 |
| `EventCalendarSource` | Scheduled market events | F1 |
| `TaxRegime` | A country's account types and tax rules (07) | C1 (hooks from B1) |
| `CalendarSource` | Exchange and series holiday tables, as versioned data | A1 |

## Self-describing
Each plug-in exports a description (`PluginInfo`): key (never changed once data exists), name, what it provides (kinds, tickers or series, currencies, markets), suggested role, the provider's limits (requests per minute/hour/day, symbols per month), whether it needs a key and which env variable, a link to the provider's terms, and flags:
- `noAi`: the provider's terms forbid giving its data to AI models. Its raw values are left out of the MCP server and AI exports.
- `unofficial`: not an official API (shown in Settings and the data-health page).

Each job run saves the descriptions to the database. The web app lists them in Settings, where the admin turns them on, orders them and assigns roles. Plug-ins suggest; the admin decides.

## Safety built into the SDK
- Plug-ins never call `fetch` directly. They use the HTTP client the core hands them, which keeps the provider's declared pace and caps (never above 80% of any limit), retries server errors with backoff, and stops that source for the run on 403, 429 or a captcha (never works around a block).
- Sources run one after another, each with its own client.
- Plug-ins return data; core validates it (layer A) before anything is stored. A plug-in cannot write to the database directly.
- Jobs and plug-ins refuse to run when `VERCEL` or `CI` is set.

## Where plug-ins live
| Folder | For |
|---|---|
| `plugins-public/` | Public plug-ins (official APIs: Tiingo, FRED, ECB, Alpaca/Massive; the Japan tax regime) and the templates |
| `plugins/` | The admin's own plug-ins, usually a private git repo mounted as a submodule (the owner's: `saku-private`). A missing folder is skipped: the public repo builds, tests and runs without it. |

## Templates
Runnable templates in `plugins-public/template/`: a `BarSource` for a made-up provider and a `TaxRegime` for a made-up country (one taxable account, one tax-advantaged account with an annual limit), each with fixtures and a passing test. A new plug-in starts by copying a template. `docs/plugins.md` documents every interface method and a checklist before turning a source on (terms checked, `noAi` set when needed, tests on fixtures pass, one real run looks right, role starts as secondary or check until its numbers agree).
