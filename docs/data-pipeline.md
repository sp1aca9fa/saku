# Data pipeline

How data gets from the sources into Saku and how it is checked. Requirements: `docs/requirements/04-data-pipeline.md`. Status: Stage A1 (ingestion, adjusted series, layers A-C) and the first A2 parts (health status, the stand-in rule; the decision-margin test comes with the strategy engine); the fault-injection suite, the weekly run and layer E on stored data (A3); source roles and the CSV fallback (A3); issuer data (layer D, advisory) in A3.

## Flow

1. **Hourly check** (`saku-daily.timer`, :20): `pnpm probe`, then `pnpm daily`.
2. **Daily job**, once per trading day: the target date is the latest NYSE session past 20:00 New York time (`SAKU_DAILY_AFTER`). Already stamped: exit, unless a red re-check is open (below): then the daily job runs again for the day (a re-check run).
3. **Ingest** (`plugin-sdk/jobs/ingest.ts`): every bar source in turn, for every active symbol, the last 10 sessions up to the target; then series (FRED `DTB3`, `SP500`) and FX (`USD` + base currency) from every source that supports the pair; then issuer data (layer D) from every issuer source with a role, for each active symbol it supports.
4. **Store** (`db/market.ts`): see Storage below.
5. **Verify** (`plugin-sdk/jobs/verify.ts`): canonical bars from the primary with our adjusted series; layers A-D; results stored.
6. **Backup**, then the stamp and the healthchecks.io ping, only when every source answered for every item (issuer sources aside: best effort, below).

`pnpm bootstrap` fetches full history (from each symbol's inception, within each plan's history limit) and checks it; `pnpm checks` reruns the checks over full history.

A source that refuses (403, 429, a challenge page) or would pass 80% of a declared limit stops for the run; any other failure is recorded for that item and the run goes on. A source whose key is missing is skipped. Either way the run is incomplete: no stamp, no ping, retried at the next check.

## Storage

- **Raw bars** (`bars_raw`): every bar as each source sent it, keyed by symbol, date and source. Never deleted. A changed raw field (open, high, low, close, split-adjusted flag, volume, dividend, split) is logged in `bar_revisions` (old, new, when, run) before the row is updated. A date a source stops returning is kept and reported.
- **Series and FX values** are append-only: each vintage is a row with its `known_at`. A refetch that reports a stored value differently (same date and publication time, or the same date when the source gives none, as for `SP500`) is a revision: a new row known from its fetch (never from the original publication time, so a read before the fetch keeps the old value), the old row kept; counted as revised in the source's summary and included in the weekly revisions summary (series or pair, `value` or `rate`, source, count, dates). A new publication time is a new vintage, not a revision.
- **Provider adjusted closes** keep the latest snapshot. A rewrite of past values (after a dividend or split) is one `readjustments` event per factor, not one revision per day. Each source declares its relative rounding (`adjCloseRounding`, default 1e-9 for double precision, at most 1e-5, below the smallest real re-adjustment such as 0.01 on 500 = 2e-5): a change within it of the stored value (ratio new / stored within it of 1) is stored with no event; consecutive changed dates whose ratio is within it of the event's factor (its first date's ratio) form one event. Yahoo declares 1e-6: its values are single-precision floats (relative rounding at most 2^-24, about 6e-8 per value, so up to 2.4e-7 between two ratios), with margin for its recomputation; not yet measured. Raw fields are compared exactly (revision log), never with this tolerance.
- **Measuring a rounding:** `pnpm sources readjustments [--source <key>] [--run <id>]` prints, per source, one run's events (default: the latest bootstrap or weekly run that stored any): their count, the 50th, 90th and 99th percentiles (linear interpolation between ranks) and the largest \|factor - 1\|, how many are within 1e-9 to 1e-4, and the same by the level of the stored adjusted close on the event's first date (< 10, 10 to 100, >= 100, unknown). A relative (float) rounding shows the same spread at every level; a fixed number of decimals shows more at low levels. Events stored before a source declared its rounding include its noise; later ones only what is above it.
- **A source's unfinished day is not stored.** A plug-in returns only final data within the asked range; job runs give it their final time (`ctx.finalAfter`, `SAKU_DAILY_AFTER`, default 20:00 New York; a value that is not `HH:MM` stops the run). Yahoo leaves out a bar before that time on its session (20:00 without one; the bar's dividends and splits come with it in a later run) and an FX rate before its London day is over, both of which Yahoo adds whatever the window; Alpaca ends requests 16 minutes before now. A later run's window covers the date. A final time before 20:00 New York leaves the target day's rate from a London-day FX source (London midnight is 19:00 or 20:00 New York, by the clock changes) to the next run's overlap window.
- **Series and FX** keep every vintage: a value is stored only when it is new for its date and publication time. `known_at` is the publication time as UTC ISO text, or the fetch time when the source gives none; a publication date without a time of day is refused (read as midnight it would make a value known hours early). FRED gives only the vintage day: assumption, known from 18:00 New York that day (the H.15 and H.10 releases come out in the afternoon). ECB: 16:00 Frankfurt. `asOf` (A2) reads `known_at`.
- **Reading versions** (`asOf`): among the versions of a date known at the read time, the one with the latest vintage (publication time; the fetch time without one) counts, then the latest known, then the latest fetch. So a restated older vintage never outranks a newer one. Versions are keyed by the publication moment, however it is spelled; a legacy date-only publication row (stored before times were required) and the same day's instant are one vintage. Later rows of a vintage read as known from their fetch, also for rows stored before this rule.
- **Withdrawals** (`series_withdrawals`, `fx_withdrawals`, append-only): a source that revises a published value to "no value" (FRED: a `.` vintage after a numeric one) sends a withdrawal. From its known time the date has no value (reads look further back; checks see a gap); reads before it keep the old value. Withdrawals are counted as revisions and told to the admins on their own line in the weekly summary. A response with a point that is neither a withdrawal nor a finite number, or two vintages for one moment, is refused whole.
- **Vanished values** (series served without vintages, e.g. FRED's `SP500`; spec 2026-10-31 vanished-values): such a source never sends a withdrawal, a value it stops publishing simply is not in the answer. The plug-in declares an answer complete for its span (`SeriesFetch.completeSpan`: every value it still publishes from the first point's date through the requested end; FRED reads every page, refuses a page at the wrong offset, a later page announcing another count than the first, and an answer shorter than that count). On a full fetch (bootstrap, weekly) core compares it with the stored dates over the span from the first point's date to the requested end (the run's target; a date after the last point but within the request is as absent as one between points): a date in that span that has a value as read at the fetch (`asOf`, withdrawals applied) and is not in the answer gets a withdrawal known from the fetch (no publication time; reads before the fetch keep the old value), counted and told like any withdrawal. So a vanished newest value is withdrawn too, and the series' freshness and the index check grade from the earlier value (never green as if it existed). Stored dates outside the span are kept and read as before, never withdrawn: before the first point's date (the source's served span moved forward, e.g. a licence window) they are counted in the source's summary line of the run log, and only the dates newly before it (inside the previous compared span, or all of them on the first comparison) are listed in the run log, once; after the requested end they are counted on their own. Each compared span is recorded (`series_spans`, append-only; read only for that). A daily fetch never compares (its span is the overlap window only), whatever the plug-in declares; nor does a plain list (series with vintages keep the `.` path above) or an empty answer. A value that comes back later is stored as a new value from that fetch, the withdrawal kept. Assumed: a current-values answer over the source's full span holds every value the source still publishes. FX rates are not compared this way. Limit: between weekly runs, a daily run still reads a vanished value as current.
- **Issuer records** (`issuer_records`): NAV and distribution with their currency, and split per symbol, issuer source and date. A row is added only when the values for that date differ from the latest stored (a vintage, never an overwrite); reads take the latest. A response with a date twice, a value that is not a number, or a NAV or nonzero distribution without an ISO 4217 currency is refused whole (decisions log 2026-11-01, C17). For checks only: never a value used in calculations.
- **Canonical bars** (`bars`): the primary's values with our adjusted series, rebuilt by each verification run (they are derived; the raw data and its revisions are the record).
- **Closed-day bars** (requirements 04, decision 2026-11-01): a bar dated on a day the trading calendar covers and has no session gets no canonical bar, and every comparison across days (layer A moves, B, C, D, stand-ins) runs from the real session before; its raw bar, its red `A.bar_valid` ("not a trading day") and its day's grade stay stored and shown. `canonicalBars`, the one reader signals, the forward record, layer E and parity use, also leaves out such a row stored before (verify removes those inside the span it rebuilds). A date the calendar does not cover is unknown, never closed: kept, and the checks refuse it. A closed-day primary bar carrying a dividend or split makes the fund red on every session from the next one on (`closed_day_event@<closed date>` on each, every run that grades those sessions, daily and full; decisions log 2026-11-01, C19): the event is in no bar the signals read, so every return across it (a split read as a fall, a dividend missing from the total return) cannot be trusted; the event is never moved to a session (which one is a guess). It clears when (1) the source's stored raw bar on that day no longer carries the event (a corrected refetch, logged as a revision; a source that stops sending the closed-day bar leaves the stored one as it is, so that case needs (2)), or (2) an admin resolves it because the event is not real: `pnpm sources closed-event resolve <TICKER> <YYYY-MM-DD> --reason "<text>" --user <admin>` (admin only, refused while a job runs; appended to `closed_event_resolutions` (0013, append-only, triggers) with the source and the event's values as stored, who, when and why, and logged in the activity log as `closed_event.resolve`). A resolution covers only those values: if the source later changes the event, it is red again until corrected or resolved anew. It only lifts the red; the event stays out of the canonical series. `pnpm sources closed-event list [--open]` lists every such event of the bars primary (closed day, the session it is red from, dividend, split, open or resolved by whom and why). Registration lists such bars as information; a red closed day refuses only if something besides the closed-day bar is red on it (a dividend or split on that bar included), and the red sessions after an unresolved event refuse as any red day.

## Our adjusted series

A forward-accumulated total-return index, 1.0 on the first date:

    r(t) = (close(t) + dividend(t)) * split(t) / close(t-1) - 1,   index(t) = index(t-1) * (1 + r(t))

where `split(t)` is the new-for-old share ratio effective on t (2 for a 2-for-1 split) and the dividend is per share going ex on t. A later dividend never changes earlier values, so incremental and full recomputation agree exactly. Assumption: when a split and a dividend share a date, the dividend is per new share.

## Tax FX

Requirements 07 ("FX for tax"), 15 (`TaxFxSource`), 04 (sources table). C1.

- **What is fetched:** only when the install's tax regime is set and its loaded declaration is the one it was set with (`installTaxRegime`); otherwise the run logs why and fetches none (the rate names cannot be checked, and no tax result is computed then either). The pairs are the US dollar against the regime's currency (`USD<currency>`, none for a dollar regime), from every `TaxFxSource` with a role (data kind `tax_fx`), in the same window as valuation FX (daily overlap, bootstrap from 1990 or the plan's history).
- **Kinds and direction:** each rate carries its stored kind and the regime's rate name. For a pair `USDXTS` (XTS per USD), `tax_buy` is the rate at which the customer buys dollars from the bank (the bank's selling rate, e.g. TTS), `tax_sell` the rate at which the customer sells dollars to the bank (the bank's buying rate, e.g. TTB), `tax_mid` the middle rate (e.g. TTM). Which one converts purchases, sales and dividends is the regime's declaration (`fx`), never core's.
- **Checks before storing** (`taxFxProblems`, packages/plugin-sdk/src/tax-fx.ts): every rate names the requested pair, a real date (`YYYY-MM-DD`), a tax kind, and a rate name the regime declares on that same kind (a source labeling TTS as the mid is refused); a value is finite and above 0 (a rate the bank did not publish is left out, never a 0); a withdrawal carries no value; one vintage (kind, date, publication time) is stated once; on one date and publication time `tax_buy >= tax_mid >= tax_sell` (equal passes). Any problem refuses the whole response for the pair: nothing stored, the pair counted as failed (the run is incomplete, no heartbeat), up to five problems in the log.
- **Storage:** `fx_rates` and `fx_withdrawals` under each rate's kind, as vintages like valuation rates (append-only, `known_at`, read only through `asOf` with the kind). Valuation reads and checks use the `valuation` kind only, so a tax rate never values a holding. A changed stored rate is reported per pair and kind (`USDXTS tax_buy`).
- **Not checked yet:** the order against rates stored by earlier fetches (only within one response); a date the bank should have published and did not (the tax engine reads the rate through `asOf` and says when it is missing, never taking another date's); agreement between two tax FX sources.
- **Open (owner decision):** a cross-check of the tax rates against the valuation rate of the same date within a tolerance (e.g. the mid within some fraction of the ECB cross). Not built: the tolerance would be a new threshold that decides which data is trusted, so it waits for the owner.

Every check gives one result per date (green ones too), stored with the source compared. Daily runs store every result in their 10-session window; full-history runs store one summary per check (count, passed, largest deviation in the check's unit) and every non-green result.

Notes and assumptions:
- **Un-splitting:** a split-adjusted source (Yahoo: prices, volume and dividends on today's share basis) is restated as traded using its own split events: a value on date D is multiplied by every split after D (volume divided). A wrong split in that source shows up as a layer B mismatch.
- **Layer B starts where the secondary's history starts** (Alpaca 2016, Massive 2 years): a plan's limit is not a missing bar.
- **Layer C on ex-dividend days** (04: "ex-dividend days adjusted"): an index level excludes dividends but holds its constituents' drops on their own ex-dates; the ETF that tracks it (SPY, QQQ) accrues those dividends and drops by its whole distribution on its own ex-date. So the ETF's total return (price plus distribution) matches the index every day, its price return falls short by the distribution on its ex-date. Both checks therefore compare total returns: the fund's against the index, and a leveraged fund's against leverage x its underlying's (the leveraged fund tracks the index). A dividend missing from the data now shows as an index deviation (and as an `adj_return_match` deviation where a source sends adjusted closes); `leverage_track` alone misses a small one (2x a 0.25% dividend is inside its 0.5pp base tolerance). Assumption: the underlying is an ETF tracking the leveraged fund's index (all current Tier 0 pairs); a fund tracking a single stock's share price would need the underlying's price return instead (backlog: a per-symbol choice when such a symbol is added). Assumption: the daily dividend accrual (about 0.005% a day for SPY, 5% of the 0.1pp tolerance) is left uncorrected; daily financing costs of leveraged funds (about 0.02-0.04% a day) sit well inside their tolerance. Results stored before this change (price returns, red or yellow on ex-dates) are not rewritten; the next full run (weekly, `checks`) stores new results for those dates. The stand-in rule's layer C and index checks compare the same way.
- **Move flags for 2x funds** are interpolated (42.5%); the requirements name 1x and 3x only.
- **`unchanged_close`** flags a close equal to the previous session's (two days with the same close).
- **Index gaps** (`index_unavailable`): a check that could not run is never green (04: an unexpected gap of a point-in-time series is yellow; a cross-check unavailable is yellow). Before the index's first value is the provider's history limit (FRED: 10 years), not a gap, as layer B starts where a secondary starts. Index and FX values are read as known at the run (point in time, `known_at` up to the run's clock): a value published later is neither compared nor counted as fresh, also in the stand-in rule's index check. One exception, the publication lag as for the cash rate: on the run's own date the index may lack only that day's value (it has the day before); that comparison is left to the next daily run, whose 10-session window covers the date again. Assumption: `SP500`'s value for a day may not be published by the run; the requirements do not say when FRED publishes it.
- **Gate counting** (`pnpm spike`): every NYSE session from the target of the earliest daily run of any status (a run that crashed still marks the start), or from the first session on or after `pnpm spike --from <YYYY-MM-DD>` (the owner names when the count starts; earlier sessions are neither listed nor counted, and the report says how many sessions with daily runs it left out and how many of them failed; a date after the daily target is refused; any other argument is refused), through the daily target (the CLI passes it; else the latest target of a finished run) counts, from the calendar, not only the sessions that had a run. Runs start with their target recorded, so a run that never finishes still names its date. Only daily runs that finished (success or failed) and stored check results for the date count. The primary and layer B are read from the latest such run targeting the date; a secondary is available when any such run targeting the date got its bars (stage-a A1: availability per day): it has close results for the date and no `secondary_missing` (nor, from before that check, a `close_match` with the message `no secondary bar`). A run that finished as failed (incomplete, for example a secondary down) counts by what it stored, so a secondary's outage is measured as secondary availability, not as a primary failure. Layer C passes when the day's own run's layer C results (what was decided on) are all green and the index results for the date from the latest such run whose window (10 sessions before its target through the target) covers it are all green: the next run's index check for the date counts, and a failure at decision time is never dropped by a later correction (both runs' non-green results are listed, each with its run). A fund with an index and no index result for the date is not passed. It is pending only while a future daily run can still bring the result: no later finished run covering the date has stored results for it, and the daily target's window (10 sessions before it through it, the earliest any future daily run reaches) still covers the date. Otherwise it is judged: layer C not passed, "index result never arrived" (an outage longer than the window never holds the verdict back). A session without a run is failed everywhere (`no run`: primary failed, no secondary available, layers B and C not passed), except the daily target while its run has not finished: pending. The verdict covers the sessions before the first pending one. It passes only with at least 20 judged sessions (stage-a A1: 20 trading days). Below 20 it reads "not passed yet: N of 20 sessions judged", naming each ratio unmet so far (shares rounded down, so an unmet one never reads as reaching its threshold); from 20 on "passed through <date>" or "not passed" ("N sessions judged, gate needs 20"); the sessions from the first pending one on are listed, never counted as passed, and do not block the verdict on the earlier ones. A day's "pass" for a layer is all of its results for that layer green.

## Issuer reconciliation (layer D)

Requirements 04: market close vs issuer NAV within the fund's normal premium/discount, and distributions and splits matching the issuer's records; best effort, a check and not a gate. Issuer sites publish files, not official APIs, so issuer plug-ins (`IssuerSource`) are private; none is public. An issuer plug-in's roles are under the data kind `issuer` (`pnpm sources set issuer <key> check`); a source without a role is neither fetched nor checked.

- **What a plug-in returns** (`IssuerRecord`): one record per date, values as published for that date: the NAV per share on that day's share basis, never adjusted for later splits or distributions (an adjusted history reads as a premium on every day before the event); on an ex-date the distribution per share (all distributions going ex that day summed) and the split ratio (2 for 2-for-1); `currency`, the currency (ISO 4217) of the record's NAV and distribution as the issuer states it (required with a NAV and with a nonzero distribution: a record carrying either without one is refused, C17; a record with only a split or a zero distribution needs none). Records stored before C17 (2026-11-01) are kept as stored: a distribution among them without a currency is still compared as published.
- **Fetching:** each issuer source with a role, for every active symbol it `supports`, in the daily window (10 sessions) or the full history like the other sources. A failure does **not** make the run incomplete (it would stop the heartbeat on every flaky issuer site). It is logged, graded and told: the day overall is yellow `issuer_unavailable@<source>` (04 severity rules: an issuer site unavailable is yellow; the admins get the data-health alert), and each fund it failed for is graded by its staleness below. A `supports` that throws counts every fund as supported (none is left out). A source with a role whose plug-in is not loaded (the private package absent or failed to load) is logged and graded the same way: the day `issuer_unavailable@<source>`, and every fund it has records for a yellow `issuer_stale` whatever their age.
- **What a source declares** (`PluginInfo.publishes`: `nav`, `distributions`, `splits`, each `true`, at least one; refused at load otherwise): only the declared kinds are checked, below. An undeclared kind has no result (the source makes no claim; nothing compared, so nothing green) and its values in the records are ignored. With NAV declared, records are per date (a date without one is "not compared"); without, records are event dates only (a date without one has no event), and the source covers no date after its last record: a primary event of a declared kind after it, or any when the source supports the fund and has no record, is yellow "not compared: no issuer record covers this date" (unless the fetch failed or the plug-in is not loaded, which `issuer_stale` reports). A source declaring no NAV has no NAV freshness: its `issuer_stale` is yellow only when this run's fetch failed for the fund or its plug-in is not loaded (with records), never for having no record (a fund may have had no event). A source declaring NAV with records but no NAV among them is yellow `issuer_stale` ("NAV declared, none stored"). No declaration: as below, inferred from the records. A source whose plug-in is not loaded has no known declaration: it gets only the yellow `issuer_stale` "plug-in not loaded" (for funds it has records for), no comparisons (inferring from its records could read a NAV-only source's missing events as mismatches).
- **Checks** (`packages/data/src/issuer.ts`), for each symbol and each issuer source with a role, one result per check and date:

| Check | Rule | Tolerance | Status |
|---|---|---|---|
| `nav_premium` | \|close / NAV - 1\|, the primary's close (as traded) vs the issuer's NAV on the same date; a NAV not positive (whatever its currency), or without a currency, is a mismatch and never a premium. A positive NAV in another known currency than the fund's is not compared (decisions log 2026-11-01: no FX conversion): no result for that date, never a green one; it still counts as published for `issuer_stale`, and `nav_tolerance_invalid` is told only when some NAV would be compared. "Not compared" is told as counts per fund, source and currency of exactly what layer D skipped (`notComparedOf` runs its comparisons: positive NAVs on dates the primary has a bar, distributions both sides report): a warning in the run's log (dated in the run's window), a "Not compared:" line in `pnpm health` before its verdict (dated in the shown days, from the records and primary bars as stored now; no grade changes) and a column of `pnpm sources issuer-stats` (on the closes it uses) | the fund's `issuer_nav_tolerance`; none set: green, the deviation recorded (observed only) | green / <= 2x yellow / red, capped |
| `distribution_match`, `split_match` | the issuer's events vs the primary's on the same dates, within the dates both cover (the issuer's first to last record). A source that publishes NAV is compared only on dates it has a record: a primary event on a date it has none is "not compared" (yellow, issuer data unavailable), never "event missing in issuer data". A source without NAV (events only) reports every event in its range, so a date without its record reads as no event. A distribution both sides report on a date whose issuer record is in another known currency than the fund's is not compared (no result, counted as for `nav_premium`); one on one side only needs no rate and is a mismatch as usual (it catches a dividend missing from the primary); a split ratio has no currency and is compared | 1% relative (layer B's event tolerance) | an event on one side only is a mismatch; capped |
| `issuer_stale` | on the run's date, the latest NAV more than 1 session behind. With no NAV stored for the fund: yellow when this run's fetch failed for it, or when the source supports it and has stored nothing (a source that delivered NAV-less records is events-only and has no freshness) | 1 session | yellow |
| `nav_tolerance_invalid` | the stored `issuer_nav_tolerance` does not parse (only a hand edit can do that): premiums are observed only, and the day overall gets `issuer_nav_tolerance_invalid` (admins told); the run goes on | | yellow |

- **Advisory cap:** every layer D result is at most yellow (`LAYER_D_MAX_STATUS`) until the owner has set each fund's tolerance from observed data and decides that layer D may turn a day red (a decisions-log entry). So layer D warns, never applies a safe state. Results feed the symbol's health like the other layers (reasons such as `D.nav_premium@<source>`).
- **Setting** `issuer_nav_tolerance`: a JSON map of ticker to a fraction, each above 0 and at most 0.2 (20%; wider would not catch a decimal error), e.g. `pnpm settings set issuer_nav_tolerance '{"<TICKER>":0.005}'` (the whole map each time). Keys naming no active symbol are warned about when set, in every run's log and by the stats command.
- **Stats** to set it from: `pnpm sources issuer-stats [--years N]` (default 2) prints, per fund and issuer source with stored records, the days with both a primary close and a NAV in the fund's currency over the last N years, the median, 99th percentile (linear interpolation between ranks) and largest \|close / NAV - 1\|, how many days were left out (stand-in closes, days graded red: not trusted primary values), how many NAVs and distributions were not compared because their record is in another currency (per currency; a NAV on a day left out counts as left out) and the tolerance set.

## Data health

Each run grades every symbol and trading day (`data_health`, and `bars.status` on the canonical bar), and the day overall:
- **Per symbol:** the worst of its check results that day (any source, any layer); a day only one source had a bar is at least yellow (`single_source`); a day with neither a primary bar nor a stand-in is red (`primary_missing`). A symbol the primary has no bar for at all (a new primary without its history) is red `primary_missing` too, from its first canonical bar, else its inception date (within the run's window), else on the run's date only (its stored canonical bars on those dates get that status; their values stay); it is never left out of the day. Reasons are codes such as `B.close_match@alpaca`.
- **Overall:** the worst symbol, the FX checks and, on the run's date, the freshness of the cash series, each graded fund's index series and the base-currency FX pair; the reasons name the symbols that were not green, the FX checks that failed and the series that are behind.
- **Cash series freshness** (the series a source declares as the USD cash rate, FRED's `DTB3`, on the Federal Reserve's business days): the latest value known at the run may miss only the run's own day (FRED publishes the next business day), green; 2-5 business days behind is yellow (`DTB3:stale(3)@fred`); more, no value, or no source declaring a cash rate (`cash:missing@none`), red. An unknown rate is never taken as 0%: the forward record's equity is then unknown (null) on days that need it. It grades the day overall but no symbol, so it does not apply a strategy's safe state (the rate moves the equity of cash and synthetic leverage, not the signal).
- **Index series freshness** (each active fund's `index_series` from the series primary, read through `asOf` on the run's date, on the trading calendar since the index is compared on the fund's sessions): the same rule (`SP500:stale(3)@fred`; no value or no series primary `<series>:missing@<source or none>`, red). It grades the day overall only, like the cash rate: a stale index alone never applies a strategy's safe state, since the bars themselves are checked by layers A and B. The fund still learns of the gap through its own `index_unavailable` results (yellow).
- **FX freshness** (base currency other than USD; the `USD<base>` valuation pair from the FX primary, read through `asOf` on the run's date, on the trading calendar): the same rule (`USDJPY:stale(3)@ecb`; no FX primary: `USD<base>:missing@none`, red). Where the primary lacks a rate a secondary has, the cross-check is a yellow `fx_unavailable` (table above). FX grades the day overall only, never a symbol or a strategy (04: FX health never affects a signal computed in USD). **Expected gaps:** a series or FX plug-in may declare the calendar it publishes on (`PluginInfo.calendar`, the id of a loaded calendar plug-in; ECB: `ecb-target`, closed 1 January, Good Friday, Easter Monday, 1 May, 25 and 26 December); a missing primary rate on a day that calendar is closed is green (04: known holidays of the series' calendar), not `fx_unavailable`. A declared calendar that is not loaded is warned about in the run's log and counts no day as closed. Freshness is still counted on the trading calendar: a TARGET-only holiday reads one session behind, still green.
- **Red in the lookback** (requirements 04, decision 2026-11-01): a strategy is red on day D (its safe state, recorded as such) when a ticker its signals read (the signal definitions' tickers, not those only held) has a red or ungraded day among the 10 sessions before D, the re-check window every daily run grades again (`DAILY_OVERLAP`). Reasons: `<ticker>:lookback_red@<date>`, `<ticker>:lookback_ungraded@<date>`, `<ticker>:lookback_missing@<date>`; D's own grade keeps its own reasons. The grade is the one stored now, so the day clears by itself once a later run grades it again as not red (recorded entries are never edited). Per date in the window: a canonical bar's `bars.status` (red is red; NULL is ungraded, so red: "not graded" is never clean); a session with no canonical bar (from the ticker's first one on) is red whatever is stored, since the signals read the series with that price missing: `lookback_red@<date>` when its latest symbol row in `data_health` is red, `lookback_ungraded@<date>` when there is none, `lookback_missing@<date>` when the stored grade is not red (an older row a run that stopped after removing the bar left); a session before the ticker's first canonical bar was never a session for it and counts for nothing. Only the window's sessions are read: a closed-day bar is in no series the signals read (above), so its red day keeps no strategy red. Days before `forward_records_from` are nothing special. Why this cannot turn every day red after a bootstrap: every verify run, daily or full, grades every session from the primary's first bar and rewrites `bars.status` of every canonical bar it builds (only the stored `data_health` rows are limited to a daily run's window), and removes the stored canonical bars it no longer builds (below), so no NULL or stale status is left from the primary's first bar on (a test runs a daily check over NULL statuses and finds none left).
- **Red re-check before execution** (requirements 04, decisions log 2026-11-01, C16; `plugin-sdk/jobs/recheck.ts`, `forward.ts`, migration 0014 `red_rechecks`): a strategy's day red at its first grading (the forward decision red, red in the lookback included) is not recorded at once. Its deadline is the next session's regular open (09:30 New York, from the trading calendar, daylight saving followed; never a fixed UTC offset) less `red_recheck_minutes_before_open` (default 60, 0 to 600), stored with the re-check when it opens. When the run's next hourly check still comes before the deadline (the run's start + 60 minutes <= deadline, `RECHECK_PERIOD_MINUTES` the timer's period; the start is when the run started its work, read after it took the jobs lock, never the timer's tick, so a run that started late counts no check that may not come) and the forward step is not past it, a re-check opens: the first red time, reasons and decision (the provisional message's fallback) are stored, no entry is appended, and the version's later days wait for it (the chain order). Otherwise (a late run) the safe state is recorded at once as before, the re-check stored as `not_rechecked` (its safe-state alert says so). Every run then grades the open day again on the data as stored then (each re-check run fetches the 10-session window and checks it first): not red and graded at or before the deadline (the forward step's clock), the normal decision is recorded (`cleared`); still red in the last check before the deadline (decided by the run's start: no later check is counted before start + 60 minutes, also when the step itself ends a few minutes past the deadline), the safe state (`safe_state`); a run started past the deadline (the machine missed the last check), or a grading past it that is not that last check, the safe state as the provisional message gave it (`late`), whatever the day grades now, so nothing known after the deadline enters the record. A day clears only when its checks pass on corrected data; no check is loosened. The entry carries `finalDecidedAt` (the forward step's clock: when the final instruction was decided) in its hashed text; the first red grading (time, reasons, deadline, outcome) is a `red_recheck` annotation; the entry, the closed re-check and the annotation commit in one transaction. The time the final message was sent (once it reached every channel; the same run sends it right after, a failed delivery at the next run; the last channel's delivery time) is a `red_recheck_sent` annotation (`sentAt`, the outcome, `finalDecidedAt`), written with `final_sent_at` in one transaction, so the record keeps the final instruction with the time it was sent. A message is marked as told with the number of channels it reached (`provisional_channels`, `final_channels`, migration 0015); one that reached none (a library version, an owner with no channel) records 0, no sending time and no annotation, and is not looked at again. The re-check row's recorded values are never changed and each later column (sending times, channel counts, final time, run, outcome) is set once; a sending time goes with a count of at least one (triggers). A setting that does not parse (a hand edit) or a calendar that does not cover the next session leaves the deadline unknown: no re-check opens (the safe state at once) and the run names the setting. Alerts: the provisional message once the re-check opens, one final message per strategy and day (the normal instruction, or the safe state stands, or late), each idempotent per (version, date, type), retried at the next run when undelivered; a re-checked day gets no second day alert. A re-check final (cleared, stands, late) or the safe-state alert of a day not re-checked, made after its execution point (the next session's open for `next_open`), says the instruction applied at that open, never "trade at" a time already past; every other alert keeps its plain timing. When every open re-check is past its deadline and the latest re-check run, started after them, failed naming each of those versions, the hourly check starts no further re-check run (`dailyAction`): that run's job-failure alert stands until an admin fixes the cause and runs `pnpm daily --force`.
- **Canonical bars are rebuilt, never left stale:** canonical bars are derived from the raw bars. A stored canonical bar dated from the primary's first bar to the run's date that the run's build no longer produces (a stand-in a later run refused while the primary still lacks the day, a date the primary no longer has, a bar on a closed day once the build leaves such days out) is removed by verify; the raw bars, their revision log and the `stand_ins` row stay. Each removal is a warning in the run log (`<ticker> <date>: canonical bar removed ...`, with its source, whether it was a stand-in, its close and its last grade); the activity log is for admin actions, and verify's other derived writes (canonical bars, grades) are not in it either. The day is then read through its grade: outside the run's window every row of that day is stored too (the overall row and each symbol's, as a daily run stores its window), so an older greener row (the stand-in's yellow) is never the latest and `pnpm health` shows the day as this run graded it. Bars before the primary's first bar (kept from an earlier primary, graded by no check) are left alone; registration refuses them. The forward step, its catch-up of missed days and `pnpm drill red` decide through the same functions (`healthOf`, core `forwardDecision`); recompute compares only the engine's signals on a safe-state day, so it agrees.
- Daily runs store every row in their window. Full-history passes store the non-green symbol rows, each symbol's graded date range (`health_coverage`) and the overall row of every date they graded, green included, in that order: a missing symbol row is green only inside that symbol's range, on a date with the overall row. Check results are stored as "Storage of results" says (requirements 04).
- **Report** (`pnpm health [--date <YYYY-MM-DD>] [--days <N>] [--lang <code>]`, read-only; default the last 5 trading days up to the latest graded date): per date the overall grade and each symbol not green, with the reasons in words, as the latest finished run covering the date graded it. Only runs that stored something count (one that failed before storing anything does not hide older grades). A daily run covers 10 sessions before its target through the target; no row = not graded. It also covers an earlier date it stored the overall row of (verify does so for a day whose canonical bar it removed, with every row of that day), so the newest stored grade of such a day is shown. A bootstrap, weekly or checks run covers every date through its target; no overall row = not graded, and a missing symbol row = green only inside that symbol's `health_coverage` range for the run (and not when one of the run's non-green check results for that symbol and day lacks its row). Full passes from before `health_coverage` read "not graded" for those symbols until the next one. Series freshness (cash rate, index, FX) is graded only on a run's own date: for an earlier date, the freshness reasons and the FX cross-checks that could not run (`fx_unavailable`) of the latest run that targeted it are merged into the overall grade, so a day graded for them never reads green later. A symbol before its first canonical bar is left out unless its inception date is on or before the date (then not graded). A date or symbol nobody graded is "not graded", never green. The header names the latest run (type, target, status, error, heartbeat). It ends with a verdict in words: `Verdict: all green.` only when every shown date is green overall and for every symbol, else `Verdict: not all green (N dates red, M yellow[, K not graded]).` (a date counts red when its overall grade or a symbol's is red, else yellow when one is yellow, else not graded). Exit code 0 when the report was produced, whatever the grades; 1 only for an error (a wrong argument, no database, no xnys calendar, a date that is no trading day, nothing graded yet).
- **Summary of one run** (`pnpm health --summary [--run <id>] [--lang <code>]`, read-only; to explain what a full check found, stage A1 "every failure explained"): by default the latest finished bootstrap, weekly or checks run that names its target and stored something (the runs the report counts); `--run` picks any run (a daily one covers its window only; one still going may be incomplete). It prints the run, whether it is complete (it succeeded, which is what guarantees every row was stored since a run is marked successful only after verify returned, and it stored the overall row of its target, the sign it graded its own date; otherwise "incomplete: not all rows stored"), its check results by status (green from the run's per-check counts `check_summaries` for a full pass, which stores only non-green results; "unknown" without them or for an incomplete run, never 0; a warning when those counts and the stored results disagree), its non-green health rows (overall and per symbol, since a single source, a stand-in or series freshness grade a day without a check result), then one row per (status, layer, check, symbol or `day`, source) of its stored non-green check results: count, first and last date, the reason in words (the report's texts), red first, then by count; then its non-green health rows grouped the same way by (status, stored reason code, symbol or `day`), so a day made red or yellow without a check result (a single source, a missing primary, a stand-in, series freshness) is explained too. Only the reasons stored on that run's rows are used (nothing merged from other runs); a row with several reasons counts under each. A row stores only its worst status, so each reason's own status is derived from the same run: single source, a stand-in and issuer data unavailable yellow; a missing primary and a refused stand-in red; series freshness and an FX cross-check that could not run as `carriedReasonStatus` grades them; a check's code from that run's result of the check, source, symbol and date; a symbol named on an overall row from that symbol's row that day. A reason whose status cannot be known (no matching result, an unknown code, a row without a reason, shown as "no reason stored", or a derived status that is green or worse than the row's own, which contradicts what was stored) is listed "in a red row" or "in a yellow row", never under a status it may not have. Unlike the report, the unit is one run's stored results, not the deciding run per date. `--check <name> [--symbol <ticker>|day] [--source <id>]` lists that check's non-green results by date (status, observed, expected, tolerance, message), at most 200 with an "N more" line. Unknown flags, runs, checks (none in the run's results or per-check counts), symbols and sources (no stored result of that check from it in the run; a full pass stores only non-green ones; results without a source are listed by leaving `--source` out, never offered as a source name) are refused; a symbol the run did not grade (outside its `health_coverage`, or for a daily run without its rows) reads "not graded by this run", never "no non-green result". `--values` adds the stored values behind the results (spec 2026-11-01 health-values, to explain a failure without server access): for each non-green group (`--status red|yellow|all`, default red) up to `--per-group <N>` dates (default 5, 1 to 50; the first and the last always, the others evenly spread; with 1, the first), each with its result (status, observed, expected, tolerance, message) and the inputs that check compared, read the way verify feeds the checks: for the bar checks (layer A, `close_match`, `dividend_match`, `split_match`, `secondary_missing`) every bars source's raw bar (a source with a role and no bar shows "no bar") on the date and on the primary's previous date (layer A also the checked source's own previous bar): close, whether it is split-adjusted, split factor, dividend, provider adjusted close, and the close and dividend as compared (un-split), up to the run's target; and the canonical bars (close, split, dividend, our adjClose, source, stand-in, status). The returns, differences, tolerances and statuses below are the checks themselves (`adjReturnCheck`, `leverageCheck`, `indexCheck`) run now on the arrays verify gives them, their result for the date ("status now"), never a copy of their math. `adj_return_match` adds our return (total-return index over the un-split primary) and the provider's from its adjusted closes on both dates, the difference and the tolerance. `leverage_track`: the fund's and the underlying's un-split primary bars on both dates, the fund's total return, the underlying's total return, the leverage, expected, difference and tolerance (as the check compares now, over the whole history up to the run's target, so the three-days-in-a-row rule applies; a result stored before the total-return change carries the price return in its own line); a streak (the message names one) also shows the two days before it. `index_match` and `index_unavailable`: the fund's bars on both dates, the index series on both dates from every source (the version that holds now through the point-in-time read, its known_at and published_at, the number of stored versions; a withdrawn value reads `- (withdrawn)`), the fund's total return and the index return from the series primary's values known now (as the check compares now); a result from another series source than the primary now says so. `fx_match` and `fx_unavailable`: every stored rate on the date for the pair the run's overall reason names (`<pair>:B.<check>@<source>`; every pair stored that day when no reason names one), per source (with a role or stored) and kind, read the same way (the header says the run compared the `valuation` kind only); a source with no rate reads "none stored". Any other check shows its result line only. Bar revisions of a shown symbol and date are listed (source, field, old, new, detected). Everything is read as stored now (the source roles, a fund's underlying and index too), not necessarily what the run saw; the output says so; a missing value prints `-`, never 0; numbers carry up to 10 significant digits. With `--check`, `--values` lists at most 50 results, each followed by its values (a block the same as the one before it reads "values as above"); `--per-group` and `--status` need `--values` and do not go with `--check`; `--values` needs `--summary`. The summary ends with a verdict: `Verdict: all green.` only when the run is complete, its per-check counts agree with its stored results, and it has no non-green check result and no non-green health row; `Verdict: incomplete run.` when it is not complete; `Verdict: not all green.` otherwise. Exit code 0 when the report was produced, whatever the verdict; 1 only for an error (a wrong argument, no database, an unknown run, check, symbol or source, a symbol the run did not grade, a run that stored nothing, no run with stored results).
- **Monthly audit report** (`pnpm audit-report [--month <YYYY-MM>] [--lang <code>]`, read-only; `pnpm monthly` on the 1st stores it in the activity log and sends its short form to the admins after the A1 gate; jobs/audit.ts, jobs/monthly.ts): one calendar month in the install's time zone. Its trading days (New York sessions dated in the month) graded as the report above grades them (a day nobody graded is "not graded", never green), each day not green with its reasons; bar revisions and re-adjustments detected in the month; quota use per provider from the ledger's day rows (UTC days; days older than the ledger's 31 days may be pruned, so such counts are "at least", never complete); every forward-record chain and anchor verified now, entries per version with their data status, safe-state days and sessions without an entry; runs started in the month, each failed or unfinished one with its first error line; stand-ins dated in the month (resolved, closed, open, reopened). It ends with `Verdict: all clear.` only when every trading day is green, every chain and anchor verifies, no forward-record day is missing, every run finished successfully, the quota use is fully known and under 80% of each declared daily and monthly-symbol limit, and no stand-in of the month is open; else `Verdict: needs attention (...)`. Revisions are listed, not judged. Exit code 0 when produced; 1 only for an error (including a month not over, or whose last trading day is not final yet).

Assumption: a failed check of a secondary also counts (a layer A failure or a mismatch above 2x tolerance is red whichever source looks wrong), since the two sources disagreeing means neither can be trusted alone.

## Stand-ins (primary missing, secondary present)

For a session the primary has no bar (from its first bar to the target date), a secondary's bar stands in when:
1. it passes layer A (structure, no move or unchanged-close flag) that day;
2. when two or more secondaries have a valid bar, they agree within the close tolerance (0.05%); the first in role order is used;
3. it passes layer C where it applies: against the underlying's canonical bars (themselves possibly stand-ins), and against the fund's index;
4. the primary has been missing at most 2 sessions in a row (the 3rd and later are refused).

A stand-in day is yellow (`stand_in@<source>`); a refused one red (`stand_in_refused:<reason>`). The decision-margin test moves every unresolved stand-in price inside the signals' lookback (requirements 04 stand-in rule 6), the day's own and earlier ones (a canonical stand-in bar whose `stand_ins` row has no `resolved_at`), each by its own band, all corners together; more than 4 such prices (counted per ticker and date) is red. The lookback is what the engine reads for the day, per signal ticker the longest of its operands, in the ticker's own bars up to the day: a price 1 bar, an SMA of n n bars, a volatility of n n + 1 bars (core `signalLookbacks`). For an operand reading total return, a stand-in on a day with a distribution counts at any age, since its close moves every later level of the total-return index (elsewhere the shift cancels in the next day's return). A signal's tolerance band keeps the previous state while the value stays inside it, so an older price can still reach the day through that state: a stand-in outside every window also counts while a comparison reading its ticker has kept the same state on every evaluated day from the last one whose value read it (or the last before it) through the day; a change after that is the value leaving the band on its own, so the state no longer rests on the stand-in. (Each comparison's states come from the engine run on the comparisons alone, since a state belongs to its comparison.) This errs toward counting: a state kept because the value is beyond the band also counts. Older stand-ins otherwise are neither moved, counted nor named. An earlier one names the strategy's day yellow ("secondary source only", `<ticker>:stand_in_lookback@<date>`) when no signal can flip, else red (`<ticker>:decision_margin`). A resolved stand-in is no longer moved, nor is one an admin closed (rule 5, below; `isOpenStandIn`). An unresolved stand-in the primary never fills keeps a strategy reading that ticker at least yellow while it is inside the signals' lookback (or until it is resolved or closed). The stand-in correction step decides the corrected allocation with the day's health as graded now (not all green), so a day still red for another reason (a red day in its lookback) stays in the safe state in the comparison. Each stand-in records its **band** for the decision-margin test (A2, with the strategy engine): the close tolerance when two secondaries agreed, else the index tolerance (0.1pp) when the index check passed, else the layer C tolerance of that day; with no independent check at all (a 1x fund without an index, one secondary, or the day after a gap), the layer C base tolerance (0.5pp), recorded with basis `unchecked`. Assumption: that last case is not named in the requirements. The canonical stand-in bar carries the band and basis of the build that wrote it (`bars.stand_in_band`, `stand_in_basis`, migration 0012), which a reopened closed stand-in is tested with (below).

Stand-ins are kept in `stand_ins`. When the primary's bar arrives, the canonical bar is rebuilt from it and the stand-in row gets the primary's close and the difference; a difference above the close tolerance is logged. The stand-in correction step annotates each forward entry that used such a stand-in (`stand_in_corrected`: recorded vs corrected allocation, never an edit): the stand-in day's entry and every later entry of the version appended while it was unresolved, since their lookback may read its close (the detail names the stand-in's date, `standInDate`). A correction waits while any ticker the version depends on has an unresolved stand-in dated on or before the entry's date and on or after the version's first entry (its corrected decision would rest on a price not verified yet; an older one, such as a hole the primary never fills, is read alike by the recorded and the corrected decision, so it holds nothing back); a later run annotates it. Meanwhile recompute skips that day (its difference would be the correction, not the engine). A correction still waiting after the weekly full refetch makes that run incomplete, naming the stand-in (ticker, date) and the days it holds back, so the admins hear of it. It runs before every recompute (daily, weekly, `pnpm strategy recompute`), since recompute skips a day a correction explains: when the engine now decides exactly the corrected allocation of that day's annotation (otherwise the day is compared as usual), so a resolved stand-in that changes a day is never told as "the engine decides differently". It reads the resolved stand-ins from `stand_ins`, not only the resolving run's list, so a version skipped then (its definition did not parse, the run stopped) is annotated in a later run; once per version, entry date, ticker and stand-in date. Right after the step (daily and weekly runs), the annotations not yet delivered are told to the people who got those signals (the version's owner's channels; the admins' channels for a library version): "D's signal used a secondary price for T; the primary's price, which arrived later, differed from it by X" (X = |primary / stand-in - 1|, 2 decimals), what the corrected price would have given (or that the signal would not have changed), that the record is annotated, not changed, and that it is not a new signal, with the data health of the version's latest recorded day. Per channel and version one message: the newest correction that changes the signal in full (else the newest), each other one that changes it on a line of its own (date, ticker, recorded -> corrected), the unchanged ones counted, every one recorded in `alerts_sent` (keyed by version, ticker and stand-in date, with the entry date). Caught up from the annotations and `alerts_sent`: a failed delivery leaves the run incomplete and is sent at the next run, a channel added later gets what it was not told; `pnpm strategy recompute` only prints, the next run tells. An annotation whose detail does not read back is never told with a guessed value: the admins get one alert naming it (keyed by the annotation's id), and the run is incomplete, with job_runs.error naming it, until that alert is delivered; the record is append-only, so the cause is found and noted in the operations notes. Whether an entry used the stand-in is decided by run ids first (verify runs before the forward step in a run): appended in the resolving run (`resolved_run_id`), it used the primary; in the run that first recorded the stand-in (`run_id`), the stand-in. An entry from another run is placed by time: it used the stand-in when appended at or after the stand-in was first recorded and before it was resolved (`created_at` and `resolved_at`, compared as instants). A timestamp that is not an ISO 8601 instant leaves that unknown: nothing is annotated, the run is incomplete and the admins' job-failure alert names it. The remedy: an admin corrects that row's timestamp to ISO 8601 with a zone (e.g. `2026-01-08T21:30:00.000Z`), recording the old and new value and the reason in the operations notes; the check is never loosened. Limit: the annotation's deviation is against the stand-in's last stored close. While unresolved, a later run may replace that close (another secondary, a revised value), so an entry from an earlier run may have seen a different close than the one the deviation names; the corrected allocation itself does not depend on it (it is decided on the primary's bar). Keeping each close an entry saw is in the backlog.

**Closing a stand-in** (requirements 04 stand-in rule 5; decisions log 2026-11-01). A stand-in the primary will never replace (a lasting hole in its history) would hold corrections back and keep every weekly run incomplete for good. An admin closes it, never anything automatic:

- `pnpm sources stand-in list [--open]` lists the stored stand-ins (`--open`: the open ones, those neither resolved nor settled by a close), oldest first: ticker, date, source, close, band, age in sessions (to today, on the xnys calendar; "unknown" outside it), state (open; resolved with the primary's difference; closed with when, by whom and why, and "open again" when its canonical bar changed), and the canonical bar: "canonical bar uses it" (with "distribution day" when that bar pays one: a total-return signal reads it at any age) and, for an open one, "closable" or "not closable yet" with why; "canonical bar has another price"; or "refused, no canonical bar". After a deploy, `--open` is how old holes are found.
- `pnpm sources stand-in close <TICKER> <YYYY-MM-DD> --reason "<text>" --user <admin>` closes one. Refused, with nothing written: an account that does not exist, is disabled or is not an admin (checked first); an empty reason; a job running (the command takes the jobs lock itself, so no caller can skip it); no stand-in on that ticker and date, one already resolved, or one whose latest close is the price its canonical bar has; a date still inside the daily refetch window (closable only when the latest complete daily run's target is more than `DAILY_OVERLAP`, 10, sessions after it, since the daily runs still ask the primary for it; with no complete daily run, or an age the calendar cannot give, it is refused); no canonical bar (a refused stand-in, below); a canonical bar that is not this stand-in (another source or close than the row's). Otherwise the close is appended to `stand_in_closes` (migration 0012: ticker's symbol, date, the source, close, band and basis it accepted, admin, reason, time; append-only, triggers refuse an update, a delete or an empty reason), the activity log gets a `stand_in.close` row (actor the admin's id; ticker, date, source, close, reason), and a first close also sets `stand_ins`' `closed_at`, `closed_by` and `close_reason`. Triggers (migration 0011) refuse a close there without its admin or reason, any later change of those columns or of the row's stand-in values, and deleting a closed row; verify no longer replaces a closed row's values (an open one is still replaced by a later run's stand-in). A close made before 0012 is only in those columns and still counts as a close. A stand-in whose closed price changed (open again, below) can be closed again the same way, after the admin checked the new price: the same refusals apply, and it accepts the canonical stand-in bar as it is now, with the band and basis this build computed (a bar written before 0012 has none: refused until the next run writes it); the activity log row names the earlier close (`reclose`). Every close stays on record.
- Who: `--user` names the acting admin. The CLI runs only on the server, which only admins can reach: shell access is the authentication, and the command checks that the named account is an enabled admin. A web action (D1) must check the signed-in user instead, never a name from the request.
- Closed counts as settled while its canonical bar is still the price of its latest close (a stand-in bar from that close's source with that close: the newest `stand_in_closes` row, or for a close made before 0012 the row's values; `isOpenStandIn`): corrections behind it proceed (it is no longer a stand-in they wait for), so the weekly run is no longer incomplete because of it; the decision-margin test no longer moves it nor names it (`stand_in_lookback`): a closed stand-in inside the signals' lookback is read as an ordinary price from then on, without its uncertainty band (requirements 04 rule 5, "nothing waits on it any more"; the owner's decision). Its price stays in the canonical bar as the stand-in (nothing edited); its own day's grade (yellow, `stand_in@<source>`) is unchanged.
- When a later run builds that day from another price (the secondary revised its bar, another secondary is chosen) or refuses it, the close no longer settles it: the price the signals read is not the one the admin closed. The day is graded at least yellow with `stand_in_closed_changed@<source>` (a refused day is red already), the run log warns (ticker, date, closed price, the price now), and the margin test and the corrections treat it as open again; the close stays on record and the row keeps the price it was closed with. The margin test then moves it by the band of the build that wrote the new bar (`stand_in_band`), not the one frozen with the close (the new price may have passed weaker checks; a bar written before 0012: the widest of the row's band, the close's and the layer C base tolerance). After the A1 gate the admins are told once per close and new price (`stand_in_reopened`, `alerts_sent` subject `stand_in_reopened:<ticker>@<date>#<closed at>:<source>:<close>`, or `:refused`): the closed and the new price, that it is checked again as unconfirmed and holds corrections back, and to check the new price, then close it again. The list says "closed price changed, check the new price, then close again" (with closable or why not). A primary that arrives later is compared with the close the canonical bar last used (as an open stand-in's last stored close is), not the closed one.
- A refused stand-in (no canonical bar) cannot be closed: nothing reads its price (the day reads as missing, red while inside a signal's re-check window). Its open row keeps the corrections behind it waiting until the primary delivers the day, and the weekly run names it. If the primary never does, that stays an open item for the admin: find a source for that day (a secondary or a CSV import given a role; if the checks accept it, it becomes a stand-in that can be closed), and record it in the operations notes meanwhile.
- The next daily or weekly run (the closing step, before the corrections) annotates every recorded entry that used it while it was open with `stand_in_closed` (ticker, stand-in date, reason, close time, recorded allocation; append-only, once per entry, ticker, stand-in date and close), "used" decided as for corrections: appended in the run that first recorded it, else appended at or after it was first recorded and before the close (for a later close: appended after the previous close and before this one) (instants; a timestamp that is not one leaves it unknown: nothing annotated, the run incomplete, the admins told). Entries appended after the close are not annotated (decided knowing it was closed). Then the version's owner (the admins for a library version) is told once per version and close (`alerts_sent` subject `stand_in_closed:<version>:<ticker>@<date>` for the first close, `#<closed at>` added for a later one): the price stays and no primary price will check it, the reason, how many recorded days used it (first to last) and that their signals stay as recorded, that from now on signals read the price as it is, and that it is not a new signal, with the version's latest data health. As the stand-in is when told: already resolved (the primary arrived after the close), the alert says so instead and leaves out "no primary price will check it" and "from now on" (the correction alert tells the difference); open again (its canonical bar changed) or closed again since, it says the day has another price, checked again as unconfirmed, without "from now on". An annotation that does not read back, or whose close no stored stand-in holds, is told to the admins once and never with a guessed state (the run is incomplete until then).
- If the primary delivers the day after all (a weekly full refetch, as the date is past the daily window), verify compares it and records it as for any stand-in (`primary_close`, `deviation`, `resolved_at`: a resolution after the close; the close columns stay). A difference above the close tolerance gives the usual `stand_in_corrected` annotations (every entry appended until the resolution, those after the close too), whose detail carries `closedAt`, and the correction alert says the primary arrived after the close.
- When: only for a day the primary will not deliver (the provider confirms it, or several weekly full refetches still lack it), not for one it is late with.

## Source roles and the CSV fallback

- **Roles** are seeded from the plug-ins' suggestions on the first run of each data kind (one primary). After that the admin decides: `pnpm sources list` (roles in order, and loaded plug-ins that have none), `pnpm sources set <bars|series|fx|tax_fx|issuer> <key> <primary|secondary|check>` (a new primary turns the old one into a secondary), `pnpm sources remove <kind> <key>` (its stored data stays). The primary is never demoted or removed by itself: name its successor first, so each data kind keeps exactly one. A source without a role is neither fetched from nor checked. Role changes and imports are refused while a job runs (try again after it). Every run logs loaded plug-ins without a role. Each change is in the activity log. The Settings page replaces this with D1.
- **CSV fallback** (`pnpm csv import <file> --ticker SPY --prices raw|split-adjusted [--source csv-<name>]`): columns `date,open,high,low,close,volume,dividend,split` (only `date` and `close` required; dividend 0 and split 1 when empty). The admin states whether the prices are as traded or split-adjusted (many exports give split-adjusted closes); split-adjusted ones are put back on the traded basis with the file's own split column, like any split-adjusted source. Validated before anything is stored: plain decimal numbers, `YYYY-MM-DD` trading days inside the calendar, in order, each once, and layer A's structure checks on every bar (missing trading days in the file's range are listed as a warning, since a fallback may cover some days only); unknown columns (an adjusted close, for example) refuse the file, since derived values are never imported. One bad row refuses the whole file. The bars are stored as raw data of their own source (`csv` by default, never a plug-in's key) through the revision log, and are used once that source has a role, like any source: as a secondary to cross-check, or as the primary while the main source is down (then `pnpm sources set bars <main> primary` again). The next run's checks grade them.

## Quota guard

- **Rule** (requirements 04): each plug-in declares its provider's limits (`perMinute`, `perHour`, `perDay`, `symbolsPerMonth`); the SDK never goes above 80% of any of them (at least 1). The limits hold across runs, not only inside one: every run that fetches (bootstrap, daily, weekly, `pnpm probe`) counts the requests and symbols the provider received in earlier runs, and so do notifier messages (alerts, `pnpm channel test`, `pnpm alert update-failed`; counted per notifier, all its channels together, and paced together within a run; a channel the service refuses stops only itself). `pnpm verify` and `pnpm csv` send no requests.
- **Windows are rolling**: a minute, an hour and a day back from now, on the run's clock. A request that would pass 80% waits for room when that is at most 2 minutes away; otherwise the source stops for the run (`QuotaError`, reported like a block).
- **Symbols per month: a rolling 31 days.** Providers do not say whether a month is a calendar month; 31 rolling days is never shorter, so it is the conservative reading. Before a bar, metadata or issuer fetch for a ticker (and the probe's ticker), a ticker not counted in the last 31 days is refused when it would pass 80% of the limit (Tiingo: 400 of 500): that ticker fails for the run (reported like any failed ticker, so the run is incomplete for a primary or secondary source) and the source goes on, since a ticker already counted is always fetched.
- **Recorded as sent**: each request is written to `provider_usage` before it leaves (retries count), so a run that crashes keeps what it sent. It is stored at the later of the run's clock and the system clock, so an injected clock that is frozen or behind never records a request earlier than it was sent; the windows are read on the run's clock. Stored usage is read and pruned at the earlier of the two clocks, so one ahead of the system clock never drops rows still inside a real window. Per provider (the plug-in's key): a `minute` row (UTC minute, request count) and a `day` row (UTC day, request count, distinct tickers). The request windows are read from the minute rows only; the day row's request count is informational. No URL, key or body is stored.
- **Conservative counting**: buckets lose exact times, so each request counts as sent at the last millisecond of its bucket. A window never sees fewer requests than were sent in it; it may see some for up to a minute (requests) or a day (tickers) longer.
- **Unknown usage sends nothing**: if the stored usage cannot be read or a request cannot be recorded, the source stops for the run before sending.
- **Pruning**: each source's first load deletes buckets no window can count any more (minute rows older than a day, day rows older than 31 days).
- Not declared yet: bandwidth limits (backlog). Usage is counted per plug-in key (a provider id shared by several plug-ins is in the backlog).

## Fault injection (layer F)

`packages/plugin-sdk/src/jobs/faults.test.ts` runs in CI on synthetic data: a clean bootstrap, then a whole daily run (ingest, checks, forward record, alerts) with one material fault in one source's response, all sources available (a primary and two secondaries, one sending adjusted closes). A clean run is green (the control), also with clean issuer data and with a clean FX primary and secondary; SPY's index check runs in every case (the index is published the evening after, so the target day's index check is left to the next run). An FX primary without a rate on a day its declared calendar is closed stays green; on an undeclared day that day is yellow (`fx_unavailable`). Each case asserts the grade, the check that caught it (a reason on the strategy's record) and, on red, the provisional message, the safe state in the record and the final alert: a red day opens a re-check (requirements 04, "Red re-check before execution"), so the suite runs the daily job again as the hourly re-check at the last check before the deadline, on the same faulted sources (a fault is never cleared by waiting):

| Fault | Injected into | Grade | Caught by |
|---|---|---|---|
| Decimal shift (close x10) | primary; a secondary | red, safe state | B close |
| Missed split | primary; a secondary | red, safe state | B split |
| Split applied to prices but not declared | primary | red, safe state | B split |
| Missed dividend | primary; a secondary | red, safe state | B dividend |
| Dividend x10 | primary | red, safe state | B dividend |
| A provider's adjusted close off by 1% | the adjusted secondary | red, safe state | B adjusted return |
| Stale close (previous close repeated) | primary; a secondary | red, safe state | B close |
| Swapped tickers | primary | red, safe state | B close |
| Timezone shift, each bar a session late | primary | red, safe state | B close |
| Timezone shift, each bar a session early (the target day is missing) | primary | red, safe state | the 2x fund's stand-in refused (layer C) |
| Missing day; the same day sent twice (the response is refused, the run incomplete) | primary | yellow (`stand_in`) | A missing day, the stand-in rule |
| Issuer NAV off by 10% (tolerance set); a distribution missing in the issuer's data; the issuer down for days; the issuer refusing every request from the bootstrap on (nothing stored) | the issuer source | yellow, the normal signal kept (layer D is advisory); the run complete; a source that could not be fetched is told to the admins | D `nav_premium`, `distribution_match`, `issuer_stale` |
| Cash rate a week stale | the cash series | red for the day overall, admin alert; the strategy's own grade stays green (by design, above) | series freshness |
| Index source down for days (3 sessions behind, every call failing) | the index series | yellow, the normal signal kept; the run incomplete; admins told | C `index_unavailable`, index freshness |
| FX primary down, 3 sessions behind; a week behind (base JPY) | the FX primary | the day yellow; red; the strategy's own grade stays green (FX never affects a USD signal); the run incomplete; admins told | FX freshness, B `fx_unavailable` |

A day only one source had is never green (`single_source`, yellow). New data paths add their cases here.

Open (owner decision): a strategy's grade reads only the target day's bars. When a source corrupts recent days (as the early timezone shift does), those days are red on their own dates, but a signal whose lookback reads them is graded on the target day alone; in that case the 2x fund's refused stand-in made it red, a 1x-only strategy would have been yellow.

## Weekly run and `pnpm verify` (layers E and G)

- **`pnpm weekly`** (Sundays, `saku-weekly.timer`): refetches the full history from every source. Changed raw values go to the revision log (`bar_revisions`, old and new value) and the admins get one summary per run (ticker, field, source, count, dates), after the recompute of every recorded day (differences annotated and told, as in the daily run). A checked backup is made first. Then the checks over the full history, a data-health alert if the day turned non-green, and layer E.
- **`pnpm verify`** (any time, no fetching; `pnpm checks` is the same): layers A-D over the full history and layer E.
- **Layer E** (`jobs/integrity.ts`), for each registered version over today's canonical bars of what it reads: core vs the reference implementation (same days, signals and allocations; equity within 1e-9 relative), and incremental vs full (the latest 20 decision days and one every 250 back, each decided and valued from the bars up to that day only, against the full pass: no look-ahead and no state that depends on later data). Stored as layer E check results (summary per check, red ones in full); a red one fails the run and alerts the admins.
- Series and FX values a refetch changes are kept as new vintages (point in time, never overwritten) and counted per source in the run log; the summary to the admins covers bars.
- **testfol parity** (`jobs/parity.ts`, layer E check `testfol_parity`): each case in `plugins/test/testfol/<case>/case.json` is backtested on the stored canonical bars (`same_close`, decisions from the whole stored history up to `to`, the curve from `from`, which must be the first decision day) and its CAGR, max drawdown and switches compared with testfol's within the requirements' tolerances. A red, ungraded or missing day of a ticker it reads in the window refuses the case; yellow days are counted. One result per case, stored in full (green included) and alerted like the other layer E results; no cases folder means no results (a log line). Case format, tolerances and known differences: `docs/parity.md`.
